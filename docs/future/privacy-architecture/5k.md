# 5k — Independent stealth-key exports and offline recovery (requirement 3q, spec 18)

**Status:** APPROVED REQUIREMENT 3q, REQUIRED BEFORE BETA EXIT — canonical in [spec 18](../../specs/18-stealth-keypair-export.md). Not future-only and not a separate feature: this entry is a cross-reference within the 5a–5l set, and the feature is counted once, as spec 18. Specification only; not implemented, tested or qualified.
**Priority and size:** governed by spec 18 and its row in the [specs index](../../specs/README.md); not separately prioritized or estimated here.
**Owner decision:** The owner approved requirement 3q (spec 18 status). As spec 18 states, that approval is not an approval to merge, deploy or publish; no authorization to activate new services or change fees.

## Goal
Ensure users can access EVM one-time payment funds without relying on the original GhostPay website or hosting.

## Normative behavior and user experience
Spec 18 is normative; this paragraph is a summary, and spec 18 governs wherever they differ. Requirement 3q: payment-level public-only or encrypted JSON export, explicitly confirmed raw per-payment EOA key export, encrypted bulk archives, and separate encrypted master viewing/spending keys. Include scheme/chain version, derivation and independently verifiable address checks. Never automatically export private keys at buyer derivation time.

## Implementation scope and interfaces
Canonical detailed spec: [docs/specs/18-stealth-keypair-export.md](../../specs/18-stealth-keypair-export.md) (approved requirement 3q, integrated from PR #190). Do not duplicate divergent crypto formats; implement only the formats, flows and acceptance tests defined there.

### Contract requirements
- Browser-facing functions have typed inputs and discriminated success/refusal results; include a stable error code and no secret payload in errors.
- Validate hostile RPC, wallet, file, URL and cross-origin inputs at boundaries; refuse unsupported chain/scheme/protocol rather than guessing.
- Existing privacy-sensitive behavior must not change silently; any opt-in private-required mode must fail closed rather than switch endpoints or settlement protocols.
- Keep all browser app private-key operations client-side and zero-install; independently operated network endpoints are optional, never required by the software publisher.

## Test and independent acceptance
The required acceptance tests are those of spec 18. Summary: independent offline decryption/import across browser/device, scalar/address test vectors, corruption, wrong password, partial import, secret-free telemetry, alternative wallet recovery and old-announcement recovery.

Required additional evidence: repository/source SHA; unit + negative tests; browser-network trace; independent review of secret flow and threat model; no live-chain or external-wallet qualification asserted until actually run. Any meaningful privacy improvement must have an observable before/after adversary test rather than subjective marketing text.

## Threat model and limitations
Raw private-key exports are bearer secrets. Master stealth keys have broad recovery power. Policy-account and Bitcoin key handling require separate specs.

## Promotion gate
Not gated as a future item. The owner approved requirement 3q and spec 18 places it before beta exit, so it is part of the beta-exit scope; the 5a–5l rule against adding items to the current beta's required gates automatically does not apply to 5k. Completion requires spec 18's acceptance tests and definition of done on one exact integrated SHA, independent security review of the secret flow and threat model, current CI and separate deployment/release authorization.
