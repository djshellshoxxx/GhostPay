# 5j — Confidential amount and settlement integrations

**Status:** FUTURE IMPLEMENTATION / SPEC ONLY (not implemented by this document).
**Priority:** P3. **Estimated size:** XL; reassess against latest code before scheduling.
**Owner decision:** Overall privacy-first architecture requested; no authorization to merge, publish, activate new services or change fees.

## Goal
Investigate genuinely confidential sender/receiver/amount settlement modes supported by independently verified chains or protocols.

## Normative behavior and user experience
Start with a comparative threat model and feasibility matrix: assets, proof generation in browser, verification, settlement finality, compliance/operational dependencies, fees, native signer support, exit/recovery behavior and non-custodial guarantees. Define explicit protocol adapters and per-capability disclosures; never label ordinary ERC-20 transfers confidential.

## Implementation scope and interfaces
Research-only until owner separately approves concrete protocol, contract risk, bridge/asset custody model and independent audit; any fund-holding contracts need high-assurance verification before integration.

### Contract requirements
- Browser-facing functions have typed inputs and discriminated success/refusal results; include a stable error code and no secret payload in errors.
- Validate hostile RPC, wallet, file, URL and cross-origin inputs at boundaries; refuse unsupported chain/scheme/protocol rather than guessing.
- Existing privacy-sensitive behavior must not change silently; any opt-in private-required mode must fail closed rather than switch endpoints or settlement protocols.
- Keep all browser app private-key operations client-side and zero-install; independently operated network endpoints are optional, never required by the software publisher.

## Test and independent acceptance
On-chain observer experiments for sender, receiver and amount leakage; proof soundness integration tests; local signing and recovery; malicious RPC/relayer; mobile resource bounds; bridge/custody rejection tests.

Required additional evidence: repository/source SHA; unit + negative tests; browser-network trace; independent review of secret flow and threat model; no live-chain or external-wallet qualification asserted until actually run. Any meaningful privacy improvement must have an observable before/after adversary test rather than subjective marketing text.

## Threat model and limitations
Confidential settlement cannot be implemented solely through UI encryption. It often needs protocol-specific contracts, assets, wallet support or different networks.

## Promotion gate
Explicit owner decision to schedule implementation, current-source/PR reconciliation, bounded design/ADR, tests, independent security review, current CI and separate deployment/release authorization. Do not add to current beta's required gates automatically.
