# Hosting, release provenance, and reproducible distribution: research for Claude

## Recommendation and scope

**Keep the existing release scripts and portable hosting kit. The next useful work is to connect them to an explicit release trust policy, qualify the exact release bytes on the promised hosting/browser combinations, and add reproducibility diagnostics.** Debian Salsa's `reprotest` and `diffoscope` are particularly good external tools; I2P's own Gitea source is a useful authoritative compatibility reference. None requires adding a runtime dependency to GhostPay's browser bundle.

This is source research conducted on 2026-11-04 UTC for the `2026-11-03-claude-handoff` batch. It compares main `0014bc5b26c7487ea1f9fb230194c36673193236` with PR #47's integrated frontier `f8193502e602c99bb24ff956f142671750b744a0`. Upstream files and licence texts were retrieved and read; no downloaded upstream code was executed. No app/build/browser/contract suite, public mirror probe, Tor/I2P service, signing ceremony, paid workflow, or publication was run. Recommendations below are implementation proposals, not a declaration that a release is qualified.

Read [the repository snapshot](00-repository-snapshot.md) for the current contribution map. This report supplements [PR #57's release qualification research](https://github.com/djshellshoxxx/GhostPay/blob/6bd5b15ce4b883b1070ccc1deef6086fd9df3aa4/docs/research/parallel-reviews/release-qualification-41750257638.md), which examined main and explicitly did not establish candidate-head equivalence. Do not convert its main-only observations into new defects on PR #47.

## 2. Highest-priority gap: release authenticity needs an executable policy

The release workflow checks that a tag is annotated and contains a PGP or SSH signature block. Its own comment and output say this **does not cryptographically verify the signature**. It subsequently builds, requests an OIDC provenance attestation over the artifacts listed by `release-out/SHA256SUMS`, and creates a draft release. The `release` environment and final publication are owner-controlled. Source can show these workflow steps; it cannot establish which required reviewers or branch protections are configured in GitHub settings. [GhostPay workflow](https://github.com/djshellshoxxx/GhostPay/blob/f8193502e602c99bb24ff956f142671750b744a0/.github/workflows/release.yml)

The best follow-up is a small policy-driven wrapper around existing Git and GitHub CLI verification, not custom cryptographic verification. Define the trusted tag signer independently of the downloaded release, the expected repository, exact source commit/ref, signer workflow, and permitted builder policy. Distinguish the following results explicitly:

- **Integrity checked:** downloaded files match the advertised checksums and manifest.
- **Tag authenticated:** the tag signature validates against the configured trusted signer and identifies the expected commit.
- **Build provenance verified:** the artifact is the subject of an accepted attestation from the expected builder/workflow/source.
- **Reproduced:** a recorded rebuild matches the selected artifact bytes under stated conditions.
- **Hosted bytes checked:** independent retrieval matches the immutable artifact file inventory, with host-only overlays recorded separately.

None of these statuses should silently imply the others. In particular, a checksum manifest and verifier downloaded from the same location are not an independent trust anchor. A signed statement establishes who made a claim; it does not itself establish application correctness, absence of vulnerable dependencies, or reproducibility. This distinction matches SLSA's [build provenance model](https://slsa.dev/spec/v1.2/build-provenance) and the [GitHub CLI verification model](https://cli.github.com/manual/gh_attestation_verify).

### Exact reusable implementation

GitHub CLI **v2.103.3**, release target commit `63837fb778d6a39f02be0ce76ff89f2bc8d74bdc`, was observed through the [release API](https://api.github.com/repos/cli/cli/releases/latest); its [tagged release](https://github.com/cli/cli/releases/tag/v2.103.3) is the stable reference. The research also inspected trunk `eeb44bc432c0107de002dadd34a61b4e2bd15882`; use the released version for an adoption evaluation, not the moving trunk snapshot.

Relevant upstream files are [`pkg/cmd/attestation/verify/verify.go`](https://github.com/cli/cli/blob/63837fb778d6a39f02be0ce76ff89f2bc8d74bdc/pkg/cmd/attestation/verify/verify.go) and [`verify_test.go`](https://github.com/cli/cli/blob/63837fb778d6a39f02be0ce76ff89f2bc8d74bdc/pkg/cmd/attestation/verify/verify_test.go). The retrieved [licence](https://github.com/cli/cli/blob/63837fb778d6a39f02be0ce76ff89f2bc8d74bdc/LICENSE) is MIT. Adoption mode: **external CLI already compatible with GhostPay's documented workflow**; do not transplant its certificate or bundle parser into shell/browser code.

The current documented command supports source commit/ref constraints, signer-workflow or exact certificate identity, issuer constraints, rejection of self-hosted runners when that is the selected policy, JSON output, and local attestation bundles. Several signer selectors are mutually exclusive, so the wrapper must choose a coherent policy instead of appending every flag. A reusable workflow's identity may differ from the calling repository's workflow identity. [CLI manual](https://cli.github.com/manual/gh_attestation_verify)

Integration points are `scripts/verify-release.sh`, `.github/workflows/release.yml`, and `docs/operators/release-and-verify.md`. Preserve the current integrity-only use case and label it accurately. Add a distinct authenticated-verification mode only once the owner supplies the signer policy. Capture the accepted artifact digest, full source SHA, tag, workflow identity, verifier version and verification result in a receipt. Do not put a signing private key in any receipt, repository, image, browser bundle or workflow source.

**Acceptance evidence:** a release fixture accepted under the intended signer/source policy; ordinary validation fixtures for an unexpected signer, different commit/ref, missing attestation and incomplete required artifact set; a clear result when only integrity checks were requested. These are specification-level verifier acceptance requirements, not an exploit reproduction exercise. The owner must first select key custody, trusted public-key distribution, revocation/rotation policy, builder requirements and whether GitHub-independent verification is required.

### Offline verification has its own prerequisite

A downloaded attestation bundle can support offline checks, but offline verification still requires trustworthy verifier software and trust-root material. The CLI documents `--bundle` and `--custom-trusted-root`; it also explains that bundle-based owner/repository name checks cannot detect later renames or reuse of the same names. Preserve the source revision and other stable identity evidence in the release receipt, and document the exact offline verification procedure before promising it. Do not label an archive “offline-verifiable” merely because its hashes can be recomputed. [CLI manual](https://cli.github.com/manual/gh_attestation_verify)

## 3. Extend reproducibility with two focused tools from Debian Salsa

### `reprotest`: vary environmental assumptions

The official Debian source repository is [Salsa `reproducible-builds/reprotest`](https://salsa.debian.org/reproducible-builds/reprotest). Stable tag **0.7.33** peeled to commit `f63779914a4926e4609068d032f2cae201c6d181` in a direct `git ls-remote` read. The retrieved [`reprotest/build.py`](https://salsa.debian.org/reproducible-builds/reprotest/-/blob/f63779914a4926e4609068d032f2cae201c6d181/reprotest/build.py) contains the `environment`, `build_path`, `locales`, `timezone`, `umask`, and `VariationSpec` machinery. The inspected default branch was `main`, not `master`; the old guessed `master` raw URL returned 404.

GhostPay already varies build directory in its existing qualifier. `reprotest` provides a maintained way to add selected environmental variations and record precisely what was varied. Begin with locale/timezone/umask/path variations relevant to GhostPay's archive and bundler output. Some variations need extra Linux facilities; record unsupported variations as skipped with a reason instead of claiming full environmental independence. Preserve `SOURCE_DATE_EPOCH` as the canonical build timestamp; the [Reproducible Builds specification](https://reproducible-builds.org/docs/source-date-epoch/) defines its purpose, not a guarantee that the entire build is reproducible.

Adoption mode: **isolated developer/CI tool**, running the existing release or lean build entrypoint. Its [Debian copyright file](https://salsa.debian.org/reproducible-builds/reprotest/-/blob/f63779914a4926e4609068d032f2cae201c6d181/debian/copyright) identifies GPL-3+ generally, with GPL-2+ files in `reprotest/lib/*` and `reprotest/virt/*`, plus specific GPL-3+ exceptions to those directory rules. Do not label the whole source tree a single permissive licence or copy its internals into the UNLICENSED GhostPay kit. Distribution of any bundled tool image requires retaining the applicable licences and notices.

Integration points: `scripts/repro-check.sh`, `scripts/qualify-lean.sh`, and the `lean-candidate` job. Start as a bounded qualification job, not a mandatory full-matrix run on every commit. An independent second builder remains a separate requirement; two environments on one runner do not establish that result.

### `diffoscope`: explain differences without accepting them

Official source is [Salsa `reproducible-builds/diffoscope`](https://salsa.debian.org/reproducible-builds/diffoscope). Stable tag **336** peeled to `6f676c6bef66a9f41451b9f623de6fc6840d9b0b`. Inspected files include:

- [`diffoscope/comparators/tar.py`](https://salsa.debian.org/reproducible-builds/diffoscope/-/blob/6f676c6bef66a9f41451b9f623de6fc6840d9b0b/diffoscope/comparators/tar.py): `TarFile.compare_details` and `TarContainer` for archive structure/content diagnostics.
- [`diffoscope/comparators/zip.py`](https://salsa.debian.org/reproducible-builds/diffoscope/-/blob/6f676c6bef66a9f41451b9f623de6fc6840d9b0b/diffoscope/comparators/zip.py): ZIP metadata and member comparison, relevant to the portable hosting kit.
- [`diffoscope/comparators/json.py`](https://salsa.debian.org/reproducible-builds/diffoscope/-/blob/6f676c6bef66a9f41451b9f623de6fc6840d9b0b/diffoscope/comparators/json.py): structured JSON diagnostics for SBOM/receipt discrepancies.

The source headers and [COPYING](https://salsa.debian.org/reproducible-builds/diffoscope/-/blob/6f676c6bef66a9f41451b9f623de6fc6840d9b0b/COPYING) establish GPL-3.0-or-later for these inspected comparators. Adoption mode: **external diagnostic CLI**. Execute it only after byte comparison differs, with bounded runtime/output and retained reports; the exact byte comparison remains the qualification gate. A JSON or archive comparator's normalization must never turn different released bytes into a “reproducible” result.

The inspected moving head had an unreleased next-version changelog. Stable tag 336 is therefore the concrete evaluation pin in this note. Neither upstream tag signature nor a downloaded binary/package signature was authenticated in this research. Before installing in CI, verify the selected distribution and its published integrity/authenticity evidence through the chosen package supply chain.

**Useful receipt fields:** source and lockfile digests; exact builder image/tool versions; effective public build settings and bundled deployment/public-key digests; canonical artifact names/digests; varied factors; skipped factors; independent-builder identity if applicable; comparison result; diagnostic report digest. Existing lean receipt fields should be reused rather than superseded.

## 5. Mirror correctness: HTTP headers, origins and content integrity

### Keep header-capable and headerless modes explicit

W3C CSP defines `frame-ancestors` as an HTTP-delivered policy control that must be ignored in a meta element. Its processing rules also exclude `sandbox` and `report-uri` from meta delivery, and meta policies do not retroactively apply to content loaded before them. Therefore adding a meta tag cannot reproduce all header behavior of nginx or a configured origin. [CSP3, published draft 2026-10-27](https://www.w3.org/TR/2026/WD-CSP3-20261027/)

GhostPay already documents this distinction. Preserve it in kit receipts and product wording. A headerless static/IPFS export should carry an explicit profile/capability result, not an assertion of security equivalence. Test actual served headers and ordinary supported embed behavior through the serving profile; parsing `_headers` alone does not demonstrate that the host applied it. Optional iframe merchant integration also needs its own owner-approved origin policy. Do not weaken the normal application's framing policy as a shortcut to make an SDK demo work.

If any mirror transform changes HTML, CSS, JavaScript or the meta policy, it creates different artifact bytes. Publish that transform's input/output digests and build identity, or build it as an explicit separately qualified profile. Keep the existing `_mirror/mirror.json` overlay outside immutable content, as the kit currently does. [Mirror overlay implementation](https://github.com/djshellshoxxx/GhostPay/blob/f8193502e602c99bb24ff956f142671750b744a0/tools/portable-hosting-kit/src/overlay/mirror.mjs)

### IPFS is three different questions

1. **Origin isolation.** IPFS documentation recommends subdomain gateways for websites because a CID gets a separate origin. A path such as `/ipfs/<cid>` on a shared gateway does not provide that separation. [IPFS addressing guide](https://docs.ipfs.tech/how-to/address-ipfs-on-web/), [subdomain gateway specification](https://specs.ipfs.tech/http-gateways/subdomain-gateway/).
2. **Content verification.** An ordinary browser receiving deserialized HTML/JS from an HTTP gateway is still relying on that gateway response. Trustless gateway formats return verifiable blocks/CAR data for a client that actually validates the expected content-addressed structure. Having a CID in the URL does not prove that GhostPay's browser validated the content. [Trustless gateway specification](https://specs.ipfs.tech/http-gateways/trustless-gateway/).
3. **Publisher and version trust.** A valid CID identifies particular content, not whether the GhostPay owner approved it or whether it is the intended current version. Bind the selected CID and file inventory to the authenticated release record. Mutable names add a resolution/freshness policy; IPFS's own documentation explicitly describes ordinary gateway IPNS resolution as trusting the gateway. [IPNS guide](https://docs.ipfs.tech/concepts/ipns/).

Adoption mode: **deployment profile requirements and fixtures**. Do not add a general-purpose IPFS node, Helia stack, or custom CAR verifier to the lean application just to publish static files. If an independently trusted loader becomes a real requirement, evaluate the complete loader/bootstrap/update trust model first. A verifier served inside the same web document cannot independently authenticate that document's delivery.

Origin isolation also means a different gateway/CID subdomain can have a different IndexedDB/storage/wallet-permission context. The existing mirror overlay already warns about this. Browser recovery/import UX must handle it deliberately; never silently move secrets to a new origin. Secure-context capabilities depend on scheme, browser and policy as defined by [Secure Contexts](https://www.w3.org/TR/secure-contexts/), so a successfully fetched static page is not sufficient evidence that WebCrypto, persistence, clipboard or wallet functionality works there.

## 6. Tor and I2P: verified upstream configuration references, remaining runtime gaps

### Keep inbound hosting separate from outbound app transport

The kit's Tor profile is an inbound static-site hosting integration. It does not establish where wallet/RPC/scanning requests made by the application travel. The [Tor onion-service setup guide](https://community.torproject.org/onion-services/setup/) covers a service forwarding to a local web server; GhostPay's own Tor/I2P documentation already distinguishes hosting from application privacy.

Do not state that browser-based Tor is universally impossible. The Ethereum Foundation's [TorJS project description](https://reads.ethereum.foundation/projects/torjs/) documents Arti compiled to WASM with browser WebRTC/WebSocket gateways to TCP relays. Browser raw TCP limitations still matter, and the gateway/bootstrap model introduces its own dependency and metadata considerations. That is an outbound transport research track; it should not replace the hosting kit or be silently added to a lean release. The [private scanning report](04-private-scanning-indexers.md) owns the corresponding transport discussion.

## 7. Provenance, SBOMs and future updates

### Attach evidence without overstating it

`npm sbom` production dependency inventory, emitted application/Worker inventory, build-tool inventory, vulnerability results and licence/notice review answer different questions. Existing lean qualification limitations already say this. Preserve that distinction in any combined release receipt; an SBOM's presence is not vulnerability clearance or proof that every listed package is emitted in the lean bundle. Link build/profile evidence to the exact artifact hash and retain the complete builder toolchain inventory separately where needed. [npm SBOM documentation](https://docs.npmjs.com/cli/v11/commands/npm-sbom), [SLSA build provenance](https://slsa.dev/spec/v1.2/build-provenance), [GhostPay lean qualifier](https://github.com/djshellshoxxx/GhostPay/blob/f8193502e602c99bb24ff956f142671750b744a0/scripts/qualify-lean.sh).

The frontier manifest deliberately marks tests, fuzzing, static analysis, audits and source verification as `not-recorded`. A useful later aggregation stage can attach result identifiers, source SHAs and artifact/report digests. It must not infer a passed gate from a filename, historical green run, or generated prose. Keep it separate from deterministic payload bytes when run timestamps and builder identities naturally differ.

### TUF is useful if GhostPay later adds authenticated automatic updates

The [TUF v1.0.36 specification](https://theupdateframework.github.io/specification/v1.0.36/) defines trusted-root bootstrap, threshold signatures, sequential root rotation, version checks, metadata expiration and persistence. These address update freshness and recovery questions that a one-time signed checksum does not answer. They also introduce real key-custody, clock, expiry and availability operations.

For that future case, the maintained **python-tuf** reference implementation is preferable to inventing a browser update protocol. Inspected source snapshot: `ec01d81644a64540b1f61d3255eef178a3665f26` on `develop`; this is **a research snapshot, not a selected release pin**. [`tuf/ngclient/updater.py`](https://github.com/theupdateframework/python-tuf/blob/ec01d81644a64540b1f61d3255eef178a3665f26/tuf/ngclient/updater.py) contains `Updater.refresh` and role-loading operations. [`tests/test_trusted_metadata_set.py`](https://github.com/theupdateframework/python-tuf/blob/ec01d81644a64540b1f61d3255eef178a3665f26/tests/test_trusted_metadata_set.py) supplies useful acceptance-case categories for root rotation, thresholds, version monotonicity, expiration and metadata relationships.
