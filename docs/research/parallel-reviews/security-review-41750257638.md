## Findings

1. **Invoice integrity and seller identity are explicitly separate — fact, no new defect established.** `packages/invoice-schema/src/sign.ts:9–16,31–45,78–110` validates and canonicalizes the invoice, hashes a dedicated domain prefix, requires the matching signer key and verifies low-s compact ECDSA. Verification authenticates the embedded key, not a merchant identity. `apps/web/src/lib/pay.ts:44–75` distinguishes pinned/unpinned keys and blocks an invalid signature. `packages/invoice-schema/src/sign.test.ts:178–195` already mutates invoice leaves; `apps/web/src/lib/pay.test.ts:54–73` already checks identity wording. Reimplementing signature mutation tests or pinning is not an independent task.

2. **Payment evidence and signed receipts are distinct — fact; remaining complete-journey qualification overlaps #47.** `packages/chain-adapters/src/payments.ts:122–135,181–210,251–292` checks canonical block hashes twice, successful receipt, direct router target/calldata, exact announcement and token transfer, optional second-provider agreement and consumption identity. It intentionally leaves indirect smart-wallet calls unverified. `apps/web/src/lib/receipts.ts:110–149` verifies a seller attestation and binds digest, chain, asset, amount and signer; transaction and stealth-address comparisons apply when supplied. Its comments expressly deny independent payment proof. `apps/web/src/views/Pay.tsx:933,970` preserves that distinction. Existing real-local-chain fixtures and corruption cases are in `packages/chain-adapters/src/payments.anvil.test.ts:123–202`. Do not propose those existing protections as missing fixes. The reconciliation document's manual-digest/complete-journey gap belongs to #47 until its actual diff is available.

3. **Confirmation depth is an application policy, not consensus finality — fact; impact depends on qualification claims.** `packages/chain-adapters/src/payments.ts:160,182–186` computes `final` from head minus inclusion height, using `finalityDepth`. This is useful confirmation/reorg policy, but is not a read of Ethereum's `finalized` block or proof of an L2 settlement state. The second block read catches changes during evidence verification; it cannot prevent later reorgs. `apps/web/src/lib/scanClient.ts:188–223,287–293,410–420` handles rollback and maps evidence-backed depth to the UI's `verified` classification. Existing reorg/resume tests in `apps/web/src/lib/scanClient.test.ts:501–546` must be retained. No consensus-finality failure was reproduced; UI qualification and finality language overlap #47.

4. **Ambiguous send errors release reservations — observed branch; economic bypass is a hypothesis.** `apps/relayer/src/service.ts:562–591` reserves worst-case gas/loss before sending, but catches every `sendSweep` exception and releases both reservations. In contrast, receipt exceptions/timeouts retain reservations at `:596–616`. `apps/relayer/src/chain.ts:163–174` delegates submission to viem's wallet client. A node may accept a signed transaction before its response is lost; an exception alone does not establish non-broadcast. If repeated accepted-but-unacknowledged transactions later consume gas without reimbursement, this branch could undercount exposure. Attacker ability to induce that condition, transport retry behavior and real loss remain unproved. Existing `api.test.ts:647–655` covers definite mock failure; `harness.testutil.ts:89–100` throws **before** recording the send. This is a materially different proposed test, not the already implemented receipt-timeout fix or UTC rollover fix.

5. **Relayer accounting settles on inclusion, without explicit finality reconciliation — fact; adversarial impact unproved.** `apps/relayer/src/chain.ts:177–182` calls `waitForTransactionReceipt` without an explicit confirmation parameter and returns only status/gas used. `service.ts:618–627` releases the loss reservation on success and settles mined reverts. The interface does not carry a receipt block hash for later reorg checking. A successful inclusion subsequently orphaned could therefore leave accounting optimistic if a later canonical execution reverts. This concerns operator accounting, separately from seller scan rollback; economic relevance needs a local-chain reproduction and an explicit operator finality policy. This report does not recommend generic retry, replacement or fallback.

6. **Sweep authorization/conservation already has strong invariants — fact, no new contract defect established.** `packages/contracts/src/GhostPaySweepRelayer.sol:35–43,80–114` binds all order fields, chain and contract domain, and consumes an owner-scoped unordered nonce before external calls. `:46–59` tolerates a front-run permit while transfer allowance remains authoritative. `:118–148` enforces exact owner/destination/fee deltas and emits only after checks. Replay, front-run permits, alias-address rejection and bitmap boundaries already have tests in `packages/contracts/test/GhostPaySweepRelayer.t.sol:122–157,241–250,355–385`; conservation has an invariant suite in `GhostPaySweepRelayer.invariant.t.sol:113–116`. No duplicate contract fix is proposed.
