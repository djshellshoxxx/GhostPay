## Findings

1. **Artifact reproducibility is implemented as machinery, not demonstrated for the release candidate.** `scripts/release-build.sh` installs with `npm ci --ignore-scripts --no-audit --no-fund`, deletes old workspace/web `dist`, builds libraries/web, then emits a deterministic tarball, normalized CycloneDX SBOM, release manifest and `SHA256SUMS`. Tar ordering, ownership, modes, epoch and gzip timestamp are controlled. `scripts/repro-check.sh` compares tarball and SBOM from two directories on one host; it excludes the release manifest. Tool versions and CI URL can legitimately vary in that manifest. `scripts/normalize-sbom.mjs` normalizes UUID and timestamp, not arbitrary dependency ordering. Thus two-directory equality is a narrower claim than independent-machine reproducibility; neither has fresh results here. `ubuntu-latest`, Node major 22 and the runner’s npm/GNU utilities are not an immutable build environment.

2. **Release metadata and actual manifest inputs can diverge.** `apps/web/vite.config.ts` consumes `apps/web/deployments` or `GHOSTPAY_DEPLOYMENTS_DIR`, and embeds manifests plus `GHOSTPAY_RELEASE_PUBKEYS`. `scripts/gen-release-manifest.mjs` instead inventories root `deployments/*.json` and records the lock digest but not an explicit build-input inventory of those environment settings. **Source-supported gap:** the two directory choices differ. **Hypothesis requiring a fixture test:** a configured web manifest could be included in the artifact while absent from the release manifest’s deployment list. The tarball hash still covers emitted bytes; this does not demonstrate an authentication bypass. A reproducibility receipt must record identical manifest bytes, public keys and all other effective build configuration, not just commit and lockfile.

3. **Checksums, package provenance and release authentication are different gates.** Lock integrity records expected package bytes; it does not authenticate the publisher or establish safety. Exact pins and disabled install scripts reduce variability but do not remove compromised build-tool risk. `.github/workflows/nightly.yml` includes `npm audit signatures`, production vulnerability gating, and a non-gating full-tree vulnerability report. The production SBOM does not inventory the complete build-tool trust boundary. `THIRD_PARTY.md`’s generated count of 257 entries/six workspaces and its historical “only fsevents” install-script statement are not current evidence; today’s read-only check explicitly failed. Its discussion of multiple noble majors is a recorded concern, not a measured artifact dependency census. Do not blindly force crypto major versions through overrides.

4. **Signing has three distinct trust relationships.** `.github/workflows/release.yml` requires an annotated tag containing a PGP/SSH signature block; it explicitly does **not** cryptographically verify it. It then builds, checks hashes, requests GitHub OIDC build-provenance attestation and creates a draft release. `environment: release` is present, but required reviewers, protected tag rules and allowed signing identities live in repository settings and were not verified. A signed source tag, a GitHub workflow attestation and the compact secp256k1 signature on a deployment manifest are separate proofs. None substitutes for the others. Independent fingerprint distribution, tag verification, expected workflow/repository identity, downloaded-byte verification and independent rebuilding remain required. There is no evidence here of an actual signed release or approved production key ceremony.

5. **Browser qualification currently has a single-engine scope.** `apps/web/playwright.config.ts` defines no Firefox/WebKit projects, uses Chromium by default (optional local executable override), one worker and blocked service workers. `.github/workflows/ci.yml` installs Chromium only. `apps/web/vite.config.ts` targets ES2022 and emits module workers, without a module-preload polyfill. That target is not an empirical browser-support promise. `workerFactory.ts`, `reconciliationVault.ts`, `tags.ts` and `idbStore.ts` depend on module Workers, Web Crypto and IndexedDB; BroadcastChannel has guarded use. The existing `apps/web/e2e/flows.spec.ts` mocks RPC and checks an emitted scanner Worker. `passphrase-vault.spec.ts` is relevant recovery coverage, not proof of cross-engine or physical-device compatibility. Secure-context availability, storage failures/eviction, private-mode behavior, background lifecycle and mobile resource limits need actual results. Camera compatibility is conditional on the shipped scope; it should not silently become a core release requirement.

6. **CI definitions, historical results and documentation disagree.** Current CI splits TypeScript/tests and contract jobs, skips heavy jobs on documentation-only PRs, and runs Chromium separately. Green documentation CI cannot qualify an application revision. Current nightly contains Echidna and Mythril jobs while `docs/operators/release-and-verify.md` says no harness/configuration exists; configured jobs are not successful execution evidence. That document’s “workflows have never run” also cannot be treated as current given the later reconciliation’s hosted-check observations. README/operator warnings that manifest signatures and bundle pinning are wholly absent lag `apps/web/vite.config.ts`, `apps/web/src/lib/manifest.ts`, `apps/web/scripts/validate-deployments.mjs` and `docs/DEPLOYMENT_MANIFEST.md`. Tests in `apps/web/src/buildScripts.test.ts` specify empty-directory acceptance and rejection of unsigned/wrongly signed manifests when configured; they were read, not run. No Sonar scanner definition was found in the inspected `.github` workflows. An external integration may supply it; absence here does not establish absence on GitHub. Historical Security C cannot be diagnosed as PR #44’s report-mode problem or dismissed because other checks passed.

7. **Deployment capability exists; readiness remains gated.** `.github/workflows/pages.yml` implements manual main-only Pages deployment, contrary to older blanket statements that no Pages workflow exists. `release.yml` still stops at a draft, with static publishing only a commented stub. Pages configuration, environment restrictions, actual publication and production headers are unverified; a workflow is not a deployed site. Its comments correctly describe missing response-header controls on Pages. `docs/DEPLOYMENT_MANIFEST.md` documents configured signature verification and on-chain readback, while real manifests/production trust roots remain prerequisites. The lean scope requires one client-only EVM path, exclusion evidence for deferred reachable code, exact-head security/recovery evidence and independent review. Owner fee-recipient/network decisions, private review packet, professional audit, legal/privacy terms, licensing (`UNLICENSED` remains package metadata), signing trust and host controls are unresolved acceptance gates, not permission inferred from green CI. No beta network or production funding is selected here.
