The implemented core is substantial: EVM scheme-1 invoices, checkout, verified scanning, direct/relayed sweep, encrypted key storage, broad QR wiring, a reviewed ERC-6538 UI, and a recently hardened encrypted reconciliation vault. Some earlier audit prose in the repo describes older states; this assessment checks the archived source paths directly. Standalone prototypes remain separate from product flows.

There is no defensible single GhostPay completion percentage because the project has no agreed feature weights, and product behaviors cannot be sensibly averaged with human launch gates. The ranges below are implementation estimates for the explicitly listed behaviors. They are not security, deployment, or launch-readiness scores.

Ranges estimate implementation only from explicitly counted behaviors: `Yes = 1`, `No = 0`, `Partial = 0.25–0.75`, and `Unassessed = 0–1`, divided by the number of implementation behaviors; bounds are rounded outward to whole percentages. Each row shows completed/total behaviors and `Yes/Partial/No/Unassessed` counts. External qualification (real-chain/device operations, hosting, audit, human review) is reported separately and never changes the implementation score. `Unassessed` is reserved for an implementation behavior whose status cannot be determined from the snapshot; external unknowns belong under Qualification. Each checklist entry cites snapshot source or, for a missing required behavior, the canonical requirement and the product boundary checked. A source file is not treated as proof of production use.

When canonical documents disagree, `docs/SPEC_REVIEW.md` correction notes take precedence, followed by `docs/COMPLETION_PLAN.md`, `docs/specs/README.md`, the developer and app/relayer specifications, `docs/MULTICHAIN_SPEC.md`, and `docs/POST_LAUNCH_FEATURES_SECURITY_ROADMAP.md`. For implementation claims, the archived source and its observed product wiring determine status; a spec or historical audit statement alone does not earn implementation credit.
