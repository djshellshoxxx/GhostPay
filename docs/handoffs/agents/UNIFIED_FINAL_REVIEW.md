## Concrete integration conclusions

### Merchant identity and fresh invoice authority

`apps/web/src/components/MerchantProfilePanel.tsx` keeps profile loading behind consent, presents the actual source origin and full signer key, and treats the remembered origin/key pair as advisory change detection. `apps/web/src/lib/embedHost.ts:57` bounds the fetch, refuses redirects and rechecks profile expiry after asynchronous work; `merchantIdentity.ts:45` serializes pin writes using nonwaiting Web Locks. The pin never becomes invoice trust or payment authorization. Remote-profile SDK launch uses an immediate popup, avoiding a pre-consent iframe handshake timeout.

`apps/web/src/lib/merchantTemplate.ts:53` verifies an owned profile snapshot and the currently loaded invoice signer. At `:71` and again after encoding, it checks recoverability/verified backup or an existing explicit waiver, session validity, request generation and profile expiry. The template's fiat minor units remain fiat and line-item data. The separately chosen fixed token amount is parsed using the chosen token's decimals. No fiat-to-token conversion or existing-invoice mutation occurs. `MerchantTemplateIssuer.tsx` invalidates issued output when editable inputs change; the panel keys the issuer by profile signature, template and amount request so a changed signed profile cannot retain an earlier request state.

`apps/web/public/ghostpay-embed-v2.js` treats `data-amount` as an unsigned request. Issuance requires signed `allowAmount` and an explicit local merchant action; an existing payer invoice remains independently signed. `invoiceCreate.ts` accepts exact template expiry seconds only within the signed-template range. Issuance explicitly rejects fiat amounts beyond the invoice schema's existing 30-digit minor-unit limit. Larger signed profile values can remain display data; they are neither truncated nor used to widen the invoice wire schema.
