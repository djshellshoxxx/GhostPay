No finding lets a remote party with no prior foothold steal a seller's keys or redirect a payment *given an uncompromised static host*. The cryptographic core is in good shape: the point validation, rejection sampling, strict parsers, AEAD/AAD use, low-s signatures, domain separation and the preview-versus-calldata assertion all held up under adversarial testing (section 4). The weaknesses are concentrated in (a) the trust anchor for contract addresses and fees (the deployment manifest), (b) things a *seller* is told to believe (scanner-reported amounts), (c) browser-persistence of the bearer link, (d) relayer availability logic, and (e) release engineering that the specs and threat model rely on but that does not exist yet.

Top findings:

1. **S3-01 (High)** The deployment manifest is the unauthenticated root of trust for the router and fee recipient; its signature is never verified and nothing is read back from the chain, so every in-app "preview equals calldata / targets manifest router" check is circular.
2. **S3-02 (Medium)** Any account can make a seller's scanner report a fake payment of any amount/token (PoC 02).
3. **S3-03 (Medium)** The full invoice link (fragment) is written to Chromium's on-disk History database despite `history.replaceState` (PoC 10).
4. **S3-04 (Medium)** Release-hash "verification" is self-attested by the same host and cannot detect the threat it is listed against; the promised release pipeline (SHA256SUMS, SBOM, signing) does not exist.
5. **S3-05 (Medium)** Relayer circuit breaker can latch in `half_open` forever; `/healthz` keeps saying `ok` (PoC 11).
6. **S3-06 (Medium)** Relayer can be made to pay gas for reverted sweeps and its breaker poisoned by anyone (design-level griefing).

## 3. Findings

Severity rationale follows impact x preconditions on the *current* code and stated threat model. "Status" is **Open** for all items (nothing was fixed; this review was read-only).

### High

#### S3-01 Deployment manifest is an unauthenticated root of trust; checks that look like verification are circular
- **Severity:** High. A one-file change at the host (`deployments/<chainId>.json`, which is deliberately *not* part of the hashed bundle and is served `no-store`) redirects every payment to an attacker router and attacker fee recipient while every client-side safety check still passes. Preconditions are modest (deploy-process or CDN/bucket write access to one JSON file, a reviewed-looking PR that changes an address), and the blast radius is all payers.
- **Where:** `apps/web/src/lib/manifest.ts:33` (loads and trusts), `packages/chain-adapters/src/deployments.ts:36,40` (the `signature` field is only format-checked, never verified; `bytecodeHashes`/`deployTx` are only format-checked), `apps/web/src/lib/pay.ts:223` (`built.tx.to` and `preview.router` are compared **with `ctx.manifest.router`**, i.e. with the same untrusted value), `apps/web/src/components/Disclosure.tsx:44` (UI admits "this app does not verify manifest signatures"), `packages/chain-adapters/src/router.ts:358` (comment: fee recipient "is not part of calldata ... must be displayed from the verified manifest"; there is no verification). `grep` for `eth_getCode|getCode|bytecodeHash` in `apps/web/src` and `packages/chain-adapters/src` finds nothing outside types.
- **Exploit scenario:** attacker alters `84532.json` (or a mirror/CDN edge serves a stale or poisoned copy): `router` = attacker contract that pulls the approved/permitted `gross` and keeps it, `feeRecipient` = attacker. The app shows the attacker's addresses as "Contract (router)" and "Fee recipient"; `assertPreviewMatchesCalldata` and `assertReadyToSend` pass because they compare calldata against the same manifest. The user approves `approve(router, gross)` or a permit for that router; funds are taken. Only a user who independently recognises the router address in the wallet prompt is protected. Threat-model row "Malicious frontend swaps recipient/fee" lists "manifest signature" and "release hash verification" as mitigations; neither works (S3-04).
- **PoC:** none needed; this is an absence of verification (confirmed by code search and by `DEVIATIONS.md` item 5).
- **Fix:** (1) Pin the expected `router`/`announcer`/`feeRecipient` per chain inside the **hashed JS bundle** (build-time constant generated from a reviewed manifest) or verify a detached signature with a release public key compiled into the bundle before use. (2) Before enabling payment, read back on-chain through the user's RPC (ideally two independent providers using the existing but unused `requestWithFallbackCheck`): `eth_getCode(router)` keccak equals `bytecodeHashes.router`, `FEE_RECIPIENT()`, `FEE_BPS()` (must be 25) and `ANNOUNCER()` equal manifest values; refuse otherwise. (3) Show the router address and `feeRecipient` as read from chain, not from JSON. (4) Add `deployments/*` to the release hash/SBOM so a mirror comparison covers it.
- **Status:** Open.

### Medium

#### S3-02 Seller scanner reports forged payments with attacker-chosen token and amount
- **Severity:** Medium. Direct financial-integrity risk for sellers (shipping goods against a fake "payment"); trivial to exploit; no on-chain value needed.
- **Where:** `apps/web/src/views/Scan.tsx:147-152` (`describe()` prints `formatUnits(metadata.netAmount)` + symbol taken from announcement metadata), `:198` (non-router case labelled "(paid directly, no GhostPay fee)"), `apps/web/src/lib/scanClient.ts:125` and `packages/chain-adapters/src/adapter.ts:225` (`viaRouter` is computed but only changes a label; matches are never verified against a transfer or balance), `packages/core-crypto/src/stealth.ts:148` (`checkAnnouncement` matches on keys only, by design).
- **Exploit scenario:** the seller's meta-address is public (it is inside every invoice). The attacker derives a valid one-time address for it, calls the canonical announcer directly with metadata `0xa9059cbb || USDC || 1_000_000_000_000`, and the seller's scanner lists "1000000 USDC ... (paid directly, no GhostPay fee)". The same works by replaying a genuine announcement (duplicate "payments"). A malicious or compromised RPC can also inject such logs (S3-14).
- **PoC:** `poc-02-stealth-edge-and-forged-announcement.mjs` section (b): `scanner matches forged announcement: true | metadata claims net = 1000000000000`.
- **Fix:** treat metadata amounts as an unverified claim. Only show an amount as "received" when `viaRouter` is true **and** the transfer is confirmed (read `balanceOf`/`eth_getBalance` of the one-time address, or fetch the tx receipt and decode the router's `Transfer`); label non-router matches "unverified announcement (anyone can post these)"; de-duplicate by `(stealthAddress, ephemeralPublicKey)`; show confirmation depth. Remove the phrase "paid directly".
- **Status:** Open (consistent with D4 in audit 04, not yet fixed).

#### S3-03 Invoice fragment persists in the browser's on-disk history database
- **Severity:** Medium. The link is a bearer secret that contains the AES key and the private line items/memo. The Playbook checklist requires that the fragment never reach history; browser-history sync would further copy it to the vendor cloud.
- **Where:** `apps/web/src/App.tsx:55-57,68` and `apps/web/src/lib/fragment.ts:19-20` (`history.replaceState`). `replaceState` rewrites the session-history entry only; the history *database* row for the initial navigation already exists.
- **Exploit scenario:** payer clicks a link or scans a QR code that navigates to `https://app/#gpi=v1....`. Anyone with access to the profile (other local user, malware, forensic image, synced device, omnibox suggestions) reads the invoice link and decrypts it.
- **PoC:** `poc-10-history-db-leak.mjs` (persistent Chromium profile, then SQLite read): `urls in History DB: [..., 'http://127.0.0.1:PORT/#gpi=v1.eyJhbGci...'] RESULT: full invoice fragment IS persisted`.
- **Fix:** cannot be cured client-side after navigation. Make "paste the link" (already implemented) and QR/clipboard hand-off the primary path, and do not put the AES key in the navigated URL: deliver the key out of band or via a two-step flow where the first navigation carries only a reference. At minimum document this and say it in the Pay-page copy ("opening links from your browser history..."); warn that a private/incognito window avoids the History DB; correct the Playbook/threat-model claim.
- **Status:** Open.

#### S3-04 Release-hash "verification" is self-attested; release pipeline promised by the spec does not exist
- **Severity:** Medium (control that cannot work against its stated threat, plus missing release gates).
- **Where:** `apps/web/src/lib/release.ts:8-14` (fetches `entryScript` from the same origin and hashes it), `apps/web/src/views/Home.tsx:19`, `About.tsx` "How to verify this release" step 1; `docs/threat-model/THREAT_MODEL.md` revenue-path row; `docs/APP_AND_RELAYER_SPEC.md` section 4 (reproducible build script, `SHA256SUMS`, CycloneDX SBOM, signed tag, deployment-manifest signing); `.github/workflows/ci.yml` (only a CI workflow; no release/publish workflow, no SBOM, no checksums, no provenance, no signing).
- **Exploit scenario:** a compromised host (or a malicious mirror) serves a modified bundle. The hash widget is part of that bundle, so it can print the "expected" hash; even an unmodified widget fetches the file again with `cache: 'no-store'` and the host can answer that request with the genuine bytes. The page therefore gives users false assurance exactly when it matters.
- **PoC:** none (logic). The code comment in `release.ts` already concedes the host-substitution case.
- **Fix:** keep the widget informational only and say so; make verification external: publish `SHA256SUMS` + detached signature (and SBOM) per tag, document `sha256sum` over the *served files* from a separate machine, add SRI/pinned hashes for IPFS/ENS mirrors, implement S3-01 pinning, and add a release workflow with environment approval and artifact attestation. Remove "release hash verification" from the threat-model mitigation column until it is true.
- **Status:** Open.

#### S3-05 Relayer circuit breaker can latch in `half_open` permanently while `/healthz` reports `ok`
- **Severity:** Medium (complete relayer outage until restart; trivially triggered once the breaker has opened, which can be induced, see S3-06; funds are not at risk).
- **Where:** `apps/relayer/src/breaker.ts:41-48` (`allow()` returns `false` whenever `current === 'half_open'`), `apps/relayer/src/service.ts:317-380` (`runJob`: `breaker.allow()` moves open to half_open; the probe only calls `recordSuccess()` at `:364` after a send; any earlier exit such as `SimulationRevert` -> `revertToError`, `gas_limit_too_high`, `budget_exhausted`, `gas_price_too_high` leaves the state untouched), `apps/relayer/src/service.ts:177` (`health()` marks `degraded` only when every breaker is `open`, so `half_open` reads as `ok`).
- **Exploit scenario:** breaker opens (RPC outage, low balance, or induced failures). After the cooldown the first request becomes the probe; if that request is an ordinary user error (a stale nonce, a simulation revert), the breaker stays `half_open`. Every later sweep gets `503 breaker_open` forever; the orchestrator sees `healthz: ok` and does not restart it. An attacker simply sends a signed-but-reverting sweep right after the cooldown.
- **PoC:** `poc-11-relayer-breaker-stuck-half-open.mjs`: step 1 `200`, step 2 breaker trips, step 3 probe returns `409 nonce_used` and leaves `breaker=half_open`, steps 4 and 5 (even one hour later) `503 breaker_open | healthz=ok breaker=half_open`.
- **Fix:** make the probe settle on every path (`try/finally`: treat user-class errors as neutral and re-arm `open`/`closed` appropriately, or let `allow()` re-admit one probe after a probe timeout); report `half_open` as `degraded` in `/healthz`; add a test where the probe request fails with a user error.
- **Status:** Open.

#### S3-06 Relayer griefing: gas paid for reverted sweeps and breaker poisoning
- **Severity:** Medium (availability + direct gas loss; economics roughly symmetric on cheap chains, which limits impact).
- **Where:** `apps/relayer/src/service.ts:332-380` (simulate, then send; `sweep_reverted` counted as breaker failure at `:375-378`), `apps/relayer/src/limiter.ts:98-117` and `service.ts:271` (per-owner quota is keyed by an address the attacker can mint at will).
- **Exploit scenario:** attacker controls a funded one-time address X, signs a valid sweep, relayer simulates OK and broadcasts. The attacker front-runs by moving the tokens out of X (or any state change the simulation depended on). The relayer's transaction is mined and reverts: relayer pays gas, earns no fee, and `recordFailure()` is called. A handful of these within the window (example config: `failureRatio` 0.5, `minSamples` 5) opens the breaker for everyone (60 s cooldown, and S3-05 can make it permanent). Per-owner limits do not help because owners are free.
- **PoC:** logic only (the breaker transition and accounting are exercised in poc-11); mempool front-running not run.
- **Fix:** do not count user-attributable reverts toward the breaker (distinguish them from RPC/send failures), use private transaction submission where available, cap unreimbursed gas per source, require a small refundable bond or fee pre-commitment (permit-funded fee pulled in a first step), and key abuse limits on something costlier than a fresh address.
- **Status:** Open (threat model lists the risk; this specific path is not mitigated).

### Low

#### S3-07 Relayer rate limiting is bypassable (X-Forwarded-For trust, IPv6, unauthenticated quote path)
- **Where:** `apps/relayer/src/server.ts:167-176,243` (`clientIp`), `apps/relayer/relayer.config.example.json:4` (`"trustProxyHops": 1`), `apps/relayer/src/service.ts:188-211` (`quote()` issues an RPC `eth_gasPrice` per call, IP limit only), `apps/relayer/src/limiter.ts:98-117` (keys are full addresses).
- **Details:** when `trustProxyHops >= 1` and the listener is reachable without the proxy (for example the Docker image: `EXPOSE 8787` plus the host must be changed from `127.0.0.1`), the client picks its own bucket with a forged header. Full-address keys also let an IPv6 /64 holder mint 2^64 buckets. If `trustProxyHops` exceeds the real number of proxies, `parts[parts.length - hops]` is `undefined`, so every client falls back to the proxy address and shares one bucket (self-DoS).
- **PoC:** `poc-05-relayer-http.mjs`: 40 requests from one client with distinct spoofed headers: `trustProxyHops=0 -> 429s=30`, `trustProxyHops=1 -> 429s=0`.
- **Fix:** bind to loopback/unix socket behind the proxy and say so in the Dockerfile/README; reject requests whose socket peer is not in a configured proxy allowlist before honouring XFF; bucket IPv6 by /64; cache gas price for a few seconds; add a global quote budget.
- **Status:** Open. Escalate to Medium if the service is ever exposed without a proxy.

#### S3-08 Secret redaction wrappers are guardrails, not a boundary
- **Where:** `packages/core-crypto/src/secret.ts:24-46` (`SecretBytes extends Uint8Array`), `:49` (`wrapSecret`).
- **Details:** `JSON.stringify`, `String`, template literals, Node `util.inspect`/`util.format` and Error-cause inspection throw as designed. These do **not**: spread / `Object.entries`, `Array.from`, `[...s]`, `Buffer.from(s).toString('hex')`, `structuredClone(s)` (returns a plain `Uint8Array` with the bytes, i.e. `postMessage` to a worker or `idb` put silently clones the secret), `s.slice()` (species override to plain `Uint8Array`), `s.subarray()`, `Uint8Array.prototype.join.call`, `TextDecoder.decode`. In browser DevTools `console.log(secret)` prints the bytes (the Node inspect hook is not used there). The `inspect`-throwing hook also makes accidental `console.log`/error printing in Node throw, which can turn a logging statement into a crash.
- **Current exposure:** the app never logs or serialises these values (bundle has no `console.` and no `sendBeacon`/XHR/WebSocket), and the worker receives a deliberately revealed plain copy. So this is Low (defence in depth). The README/DEVELOPER_SPEC language "non-serialisable types" overstates the guarantee.
- **PoC:** `poc-01-secret-redaction-bypass.mjs` prints 14 `LEAK` lines.
- **Fix:** document as best-effort; keep secrets in a closure/WeakMap-backed class that is not a `Uint8Array` subtype and exposes only `use(fn)`; add an ESLint rule banning `structuredClone`/`postMessage` of values typed `SecretScalar`.
- **Status:** Open.

#### S3-09 Direct sweep: attacker-chosen target contract and uncapped, unconfirmed fee parameters
- **Where:** `apps/web/src/views/Sweep.tsx:127` (notice says non-allowlisted tokens "will not be swept from here") vs `:159` (direct button only checks `balance`), `apps/web/src/lib/sweep.ts:163-200` (`directSweep`: `to = token` taken from announcement metadata at `:184`; `maxFeePerGas = 2 x eth_gasPrice` from the RPC at `:167-168`; broadcast on one click).
- **Details:** (a) For a non-router announcement (see S3-02) the attacker chooses the "token" address. Direct mode signs and broadcasts `transfer(dest, balance)` to that arbitrary contract from the seller's one-time address (gas burn; arbitrary code runs with `msg.sender` = the stealth address, value 0). The UI text promises the opposite. (b) A single lying RPC controls `gasPrice`, so the signed `maxFeePerGas` can be set to 90 % of the balance; the realised loss is the base fee plus the priority tip (`gasPrice/10`, about 4.5-5 % in the PoC) and needs a colluding block producer to profit, but there is no cap or confirmation screen.
- **PoC:** `poc-07-direct-sweep.test.ts`: `signed tx.to = 0x...deadbeef (NOT on the allowlist)`; `maxFeePerGas=42857 gwei ... signed max fee = 89 %, tip to proposer = 4.5 %`.
- **Fix:** enforce the allowlist in `directSweep`/`onDirect`; cap `maxFeePerGas` (absolute and relative to a second provider), show gas cost and require confirmation; refuse native sweep when fee exceeds a small percentage.
- **Status:** Open.

#### S3-10 Embed SDK is served from a mutable, unversioned URL with no SRI/hash publication
- **Where:** `apps/web/public/_headers:24-26` (`/ghostpay-embed-v1.js`, `Cache-Control: public, max-age=3600`, CORP cross-origin), `apps/web/public/ghostpay-embed-v1.js`.
- **Details:** the file is 66 lines, dependency-free and does the right things (same-origin link check, `https` or `localhost` only, `noopener,noreferrer`, no `innerHTML`, no network, no globals, no `postMessage`). But merchants include it with full privileges on their origin; there is no immutable per-version filename, no published SRI hash, and the host can replace it within an hour. The roadmap (Feature 2) calls for versioned URL + SRI + signed hash.
- **Fix:** emit `ghostpay-embed-v1.<hash>.js` per release, publish the SRI string in the release notes, keep the unversioned name only as a documented moving alias.
- **Status:** Open.

#### S3-11 Meta-tag-only hosting weakens the CSP posture; connect-src is broad
- **Where:** `apps/web/index.html` (meta CSP lacks `frame-ancestors`), `apps/web/public/_headers:5-11` (full policy only where `_headers` is honoured), `apps/web/public/_headers:1-2`.
- **Details:** **[PoC]** `poc-04`, headers mode vs meta mode: the app **cannot** be framed with headers (`Refused to frame ... frame-ancestors 'none'`) but **is** framed and renders in meta-only mode (GitHub Pages is a named target), enabling UI redress (the wallet prompt itself is not framable, which limits impact). In meta-only mode the dedicated scanner worker's script response carries no CSP, so "worker has no network access" is enforced by code review/bundle scan only, not by the browser. `connect-src 'self' https: wss:` (documented trade-off) means any future script injection can exfiltrate to any HTTPS host. `_headers` has no `Strict-Transport-Security`, `Cross-Origin-Embedder-Policy`, or `/` index rule; no `require-trusted-types-for 'script'`.
- **Verified OK in both modes:** inline scripts and inline event handlers are blocked (`script-src-elem|inline`, `script-src-attr|inline` violations), `data:` workers blocked (`worker-src|data`), foreign iframes blocked (`frame-src`), plain-http fetch blocked, zero external requests, zero service workers.
- **Fix:** treat header-capable hosting as mandatory for production (document that GitHub Pages is demo-only), add HSTS (`max-age=63072000; includeSubDomains`), consider Trusted Types, and long-term tighten `connect-src` via a user-visible allowlist step (build-time list plus per-origin consent) instead of `https:`.
- **Status:** Open (largely a documented trade-off).

#### S3-12 Invoice text fields accept bidi controls, zero-width and tag characters
- **Where:** `packages/invoice-schema/src/schema.ts:146-158` (`text()` rejects C0/C1 controls, lone surrogates and non-NFC only), rendered at `apps/web/src/views/Pay.tsx:408,420`.
- **Details:** `U+202E` (RLO), `U+2066` (LRI), `U+200B`, tag characters `U+E0041` and Cyrillic homoglyphs are accepted and displayed in memo/description (`SPOOF-ACCEPTED` x5 in PoC 03). They can reorder or hide text in the table cell or memo line. React escaping prevents injection; this is visual spoofing only (no amounts or addresses come from these fields).
- **Fix:** reject `\p{Bidi_Control}`, `\p{Cf}` (except ZWJ in emoji if wanted) and `\p{Co}`; or render the fields with `unicode-bidi: isolate; direction: ltr` and replace invisible characters with a visible marker.
- **Status:** Open.

#### S3-13 Keystore import accepts attacker-chosen scrypt cost; weak passphrase policy
- **Where:** `apps/web/src/lib/keystore.ts:31,130-132,43` (`MAX_N = 2^20`, `r <= 16`, `p <= 4`, `maxmem: 2**31`), `:33` (`MIN_PASSPHRASE = 10` UTF-16 units).
- **Details:** importing a crafted file makes the tab allocate up to about 2 GiB and spend roughly 27 s or more of CPU (extrapolated from a measured 107 ms at N=2^15; measured, not exhausted). Self-DoS only. All header fields are AAD-bound (N, r, p, salt, iv, meta, ciphertext tamper cases all rejected, PoC 08). Export parameters (N=2^17, r=8, p=1, AES-256-GCM, random 16-byte salt and 12-byte IV) are sound; a 10-character passphrase is the weak link for an offline attacker who gets the file. `NFKC` normalisation of the passphrase is applied before scrypt (compatibility risk with other implementations, not a vulnerability).
- **Fix:** cap import cost near the export profile (N <= 2^18, r <= 8, p <= 2), add a strength estimate or minimum 14+ characters / diceware guidance, document the NFKC rule in the file format.
- **Status:** Open.

#### S3-14 RPC adapter: chain id verified once, single-provider trust, hostile-log gaps
- **Where:** `packages/chain-adapters/src/rpc.ts:260` (`eth_chainId` checked only in `createClient`), `:320` (`requestWithFallbackCheck` exists but is never used by `apps/web` or `apps/relayer`), `packages/chain-adapters/src/logs.ts:145` (log `blockHash` is stored but not compared with `eth_getBlockByNumber`), `rpc.ts:75-90` (`validateRpcUrl` accepts any `https`/`wss` host, including loopback, link-local `169.254.169.254` and numeric/obfuscated forms that normalise to `127.0.0.1`).
- **PoC `poc-06`:** safe: wrong chain id at connect, oversize response (cap enforced while streaming), never-ending body (aborted at the timeout, 1501 ms), redirect (`redirect: 'error'`), batch array response, id mismatch, wrong emitter, `removed: true`, out-of-range block, garbage `data`, duplicate ids. **Accepted:** bait-and-switch (correct chain id once, wrong afterwards); a log whose `blockHash` is not the canonical hash; an entirely fabricated log. A 1 000-log hostile page larger than the 64 KB test cap raises `RESPONSE_TOO_LARGE` (works as designed; the default cap is 2 MiB). These are inherent to a single RPC; they matter because the UI and S3-02 trust the result.
- **Relayer/SSRF note:** RPC URLs come from operator config (`rpcUrlEnv`), so private-range hosts are operator-trusted; in the browser they are the user's own setting and CORS-limited.
- **Fix:** re-check `eth_chainId` periodically (or bind each request to a verified genesis/finalized hash), use two-provider reconciliation for security-relevant reads (price, allowance, getCode, block hashes), cross-check log `blockHash`, and consider rejecting private IP ranges in the browser settings with an explicit "local node" opt-in.
- **Status:** Open.

#### S3-15 Scan UI integrity and robustness
- **Where:** `apps/web/src/views/Scan.tsx:141,229` (matches are stored globally; `Matches` and `selectForSweep` use whichever chain is currently selected), `apps/web/src/lib/scanClient.ts:92,67,79` (`wait()` has no timeout; Cancel cannot unblock a hung worker reply; `createWorker()` runs before the `try`, so a throw skips the key zeroisation in `finally`).

#### S3-16 Local tag vault: ciphertext records can be spliced; metadata in clear

#### S3-18 Relayer operational hardening
- **Where:** `apps/relayer/src/server.ts:110-116`, `apps/relayer/deploy/ghostpay-relayer.service`, `apps/relayer/src/config.ts:197`, `apps/relayer/relayer.config.example.json:15`, `apps/relayer/src/secrets.ts:37-75`.

#### S3-19 Token approval is sent before the final preview and left in place on abort
- **Where:** `apps/web/src/views/Pay.tsx:285` -> `apps/web/src/lib/payExec.ts:63-80` (`ensureAllowance`).
- **Details:** for non-permit tokens, "Prepare payment" first submits an on-chain `approve(router, gross)` (exact amount, and the app verifies calldata with `assertApproveTx`), then builds the payment and shows "Final check". If the user stops there, or the payment reverts, the allowance stays; with S3-01 a hostile router could pull it. - **Fix:** prefer permit where supported (already default for allowlisted USDC), show the router/spender and amount in the same review as the final preview before sending approval, offer "revoke" after failure, and mention the linkability in the copy.
- **Status:** Open.

## 4. Checked and found safe (with evidence)

Core crypto (`packages/core-crypto`)
- **Point validation:** infinity (`0x00`, 33 zero bytes), `x >= p`, `x = 0`, off-curve `x = 5`, uncompressed `04..`, hybrid `06/07` all rejected (`INVALID_POINT`); valid `G` accepted (PoC 02a). secp256k1 has cofactor 1 and compressed decoding rejects twist points, so no small-subgroup/invalid-curve path. Meta-address with trailing newline rejected (the regex `$` is not Python-style).
- **Scalar generation:** rejection sampling in `[1, n-1]` from `crypto.getRandomValues`, 64-attempt stuck-RNG guard, buffer zeroised after copy (`packages/core-crypto/src/rng.ts:31-43`). No modulo bias. `h = int(keccak(S)) mod n` bias is about 2^-128 and zero is rejected (ADR-0001).
- **Y-parity of the ephemeral key:** flipping `02<->03` yields `S -> -S`, a different `keccak(S)`, so the flipped announcement does **not** match (PoC 02c): no malleability and no false positive. View tag is one byte of the shared-secret hash (1/256 false-positive rate by design).
- **Stealth key derivation** re-derives the address and checks equality, zero key rejected; `deriveVerifiedSweepKey` re-checks before any signing.
- **Hex/ABI parsing** (`hex.ts`, `logs.ts`): strict regex, canonical re-encode equality for log `data`, bad content skipped (not thrown), provider-level faults thrown. All regexes examined are linear (no nested/overlapping quantifiers); timing probes on 50 KB inputs: 3 ms.

Invoice schema (`packages/invoice-schema`)
- **Base64url:** strict alphabet, no padding, canonical trailing bits, length mod 4 != 1; `+ / = \n é \0` and non-canonical last symbol all rejected (PoC 03).
- **JSON:** hand-written strict parser: duplicate keys, `__proto__/constructor/prototype`, floats, exponents, `1e999`, negative, leading zeros, depth > 8 (10 000 nested `[` rejected in 0.8 ms), BOM, whitespace padding, escaped-instead-of-literal text (needs exact canonical form) all rejected; lone surrogate via `\ud800` rejected by the schema. Objects are null-prototype. 16 KiB decoded cap enforced before parsing (20 KB rejected).
- **Signature:** secp256k1 ECDSA, RFC 6979, **low-s enforced on verify** (high-s twin: `false`), domain prefix `GhostPay.Invoice.v1\0` (verifying without the prefix: `false`), digest covers the full canonical plaintext including `chainId`, `v`, `nonce`, `expiresAt`, `token`, `signer`; mutating `chainId`, `expiresAt` or `token` invalidates it (cross-chain and cross-version replay not possible). The self-asserted `signer` is correctly presented as "not pinned / not a verified seller" (`pay.ts:46-55`).
- **AES-256-GCM envelope:** random 256-bit key and random 96-bit nonce per invoice (no nonce reuse possible), AAD = `"GPI1" || chainId(u64) || signer(33)`, tag 128 bit, key/nonce/ciphertext shape-checked before use, failure to decrypt gives a fixed error. Note the AES key travels in the same fragment, so this is access obfuscation for URL/log hygiene, not confidentiality against a link holder (documented, ADR-0005).

Browser app (`apps/web`, built bundle, Chromium)
- **XSS:** React text rendering only; payload `<img src=x onerror=...><script>...` in memo and line items rendered as literal text, no dialog, no injected nodes (PoC 04, both hosting modes). No `href`/`src` derived from invoice, RPC, token or QR data; the only `<a>` is a blob download and the skip link; the only `<img src>` is a wallet icon limited to `data:image/(png|jpeg|webp|svg+xml);base64,` of at most 64 KB (SVG in `<img>` does not run script). QR is an SVG built from React elements; the download string contains only numbers and a fixed path. No `dangerouslySetInnerHTML`/`innerHTML` use in app code (React's own fingerprints only). No DOM-clobberable global lookups, no `postMessage` listener, no `window.opener` use, no `target=_blank`, no redirects from invoice data (no open redirect, no tabnabbing).
- **Fragment handling:** parsed in memory; cleared from the address bar on load and on `hashchange` (default on); zero subrequests contain the fragment; subrequests carry no `Referer`; zero external requests; no service worker; storage after key generation: `localStorage {}`, `sessionStorage {}`, no cookies, no IndexedDB databases, zero 64-hex strings in the DOM. (But see S3-03 for the History DB.)
- **CSP actually delivered:** `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self' https: wss:; object-src 'none'; base-uri 'none'; form-action 'none'; worker-src 'self'` in the built `index.html` (no `unsafe-inline`/`unsafe-eval`; the built page has no inline script/style/handler and the module script is `./assets/...`), same plus `frame-ancestors 'none'` in `_headers`, plus `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `nosniff`, a restrictive `Permissions-Policy`, COOP `same-origin`, CORP on assets and manifests. Enforcement confirmed for inline script/handler, data worker, foreign frame, plain-http fetch. `eval`/`new Function` could not be probed meaningfully through CDP, but `script-src 'self'` omits `unsafe-eval`, the bundle contains no `eval(`/`new Function`, and `scan-bundle.mjs` enforces it.
- **Embed SDK:** link must be same-origin as the script, `https` (or `http://localhost`), no credentials, bounded length, `#gpi=v1.` prefix; `window.open(..., 'popup,noopener,noreferrer')`; no `innerHTML`, `eval`, network, globals, or `postMessage` (so there is no origin-check surface to attack). If `document.currentScript` is null the SDK fails closed (buttons disabled).
- **Preview vs calldata:** `assertPreviewMatchesCalldata` decodes independently, re-encodes and compares byte-for-byte. PoC 09: mutated `to`, `value`, trailing bytes, wrong selector, empty data, upper-cased hex all rejected; **9 000 random nibble flips: 0 accepted**. Deliberately not covered (and documented): the fee recipient, ownership of the stealth address, wallet gas/EIP-1559 fields, the chain the wallet really uses (needs an independent RPC; after sending, `verifySubmission` compares sender, `to`, input, value and chain id on the user's RPC). `eth_sendTransaction` params contain only `from,to,data,value,chainId`.
- **Permit/approve:** exact-amount approve with calldata assertion; permit domain accepted only if the locally computed domain separator equals the token's `DOMAIN_SEPARATOR`; wallet-returned permit signature is recovered and must equal the payer.
- **Jitter / "nothing signed while waiting":** `startWaiting` creates only a local `DelayScheduler`; wallet discovery, connection, allowance, permit and send all start only after the `ready` phase (`Pay.tsx:175-222,244-246`); uniform sampling via CSPRNG rejection (chi-square over 200 000 samples = 12.5 for 9 dof, critical 27.9), monotonic clock, re-validation of expiry/quote/manifest at due time. Residual: opt-in, skippable ("Send now"), tab must stay open, approval tx not covered (S3-19).
- **Keystore:** every header field AEAD-bound; tampering with N/r/p/salt/iv/meta/ciphertext and a wrong passphrase all rejected with an indistinguishable error (PoC 08).
- **Worker protocol:** receives only public logs plus the viewing key once (plain copy, zeroised both sides), `error`/`onerror`/terminate handled, bundle scan asserts no `fetch/XHR/WebSocket/EventSource/sendBeacon/importScripts` in the worker chunk.
- **Wallet adapter:** account lists from `eth_requestAccounts` and `eth_accounts` must agree; chain re-read before every signature/send; `net_version` consistency probe; icons/names sanitised.

Relayer (`apps/relayer`, PoC 05)
- Body cap 16 KiB (Content-Length and chunked: both `413`), `Content-Type` must be JSON (`text/plain` -> `415`, so no CORS "simple request" path), strict field allowlists on every object (`__proto__` rejected -> `400`), 16 KiB of `[` -> `400` quickly, CL+TE and duplicate Content-Length -> `400` from Node's parser (no smuggling), `maxHeaderSize 8192`, `headersTimeout 10 s`, `requestTimeout 15 s`, `keepAliveTimeout 5 s`.
- CORS: exact-origin allowlist, no wildcard, no credentials, disallowed origin -> `403` without ACAO; `Vary: Origin`. Routes resolved with `Object.hasOwn`. Security headers set on every response.
- Quote token: HMAC-SHA-256 over a fixed, newline-delimited, lower-cased field list with a version prefix (no field-injection ambiguity), fee/expiry taken from the token and re-MACed, constant-time compare, wrong fee/expiry/destination/uppercase MAC all rejected. Fee below quote, above the 300 bps cap, `feeTo` mismatch, deadline window, signature recovery to `owner`, owner rate limit after authentication, compliance gate, then serial per-chain lane with simulation immediately before send. EIP-712 domain includes chain id and the configured relayer contract, so cross-chain/contract replay fails; the contract nonce handles replay (contract not reviewed).
- Logging is allowlist-by-construction (`log.ts:43-57`): no body, IP, address, amount, signature or free text can be logged.
- Nonce manager and budget: single serial lane, `reserve` before send and `release` on failure, so no double-spend of the daily budget in the normal path; legacy `gasPrice` capped by `maxGasPriceWei`.
- Config: strict schema, unknown keys rejected, `https`-only RPC without credentials, mainnet requires manifest and `ALLOW_MAINNET=1`, secrets from 0600 files, never in errors.

Dependencies
- `npm audit` clean; exact pins; no lifecycle scripts on prod paths; registry-only resolution with integrity; no `^`/`~` ranges.
