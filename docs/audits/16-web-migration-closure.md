## Closure status

The primary invoice, payment, scan, wallet, settings, registry, and sweep flows are adapted to the target APIs and preserve the target's newer passphrase invoice envelope, BTC flow, registry view, QR semantics, and i18n work. The important security properties are fail-closed at the points identified below. No production deployment is configured or shipped, and the default app now reports an explicit invalid manifest state when no release verification key is compiled in.

Deep-scan is surfaced as an explicit opt-in in Scan and uses the chain adapter's tag-match path; focused tag-match tests pass. Production deployment files are compiled into the bundle only after schema, chain, and release-signature validation; runtime still performs the separate on-chain readback gate. Web, relayer, and ops-monitor production consumers now all require the same structured `manifestDigest` signature and compressed-key allowlist; the raw-text verifier remains explicitly legacy-only.

## Open gaps and boundaries

1. **No production release key or manifest is supplied.** Vite accepts validated public keys through `GHOSTPAY_RELEASE_PUBKEYS`; none is invented in this work. Until operators provide a key generated and held offline, manifests cannot be added to a normal build and default deployment loading stays disabled. Manual tests may still inject a `ReleaseKey` explicitly; that does not alter default trust.
2. **No maintained offline signer command exists.** `DEPLOYMENT_MANIFEST.md` provides a mode-0600 key-file recipe that signs the structured digest and never prints the private key. A reviewed, maintained signer tool/ceremony remains open.
3. **Browser coverage uses a test-only signed release fixture.** The final 17-test Playwright run passed after the sweep, release-policy, and signed-bundle changes. The fixture key is configured only for the E2E web-server build; it is not a production release key.
