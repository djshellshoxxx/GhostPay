## Current product-code gaps and completed flows (2026-10-22)

The earlier gap list is stale for passphrase invoices, seller-key storage, basic QR rendering, seller-signed receipt issuance, and Pay-side seller-receipt import. This section reflects current code and screen wiring. The fresh signed-fixture Playwright rerun passed 17/17 after receipt integration; full web coverage and candidate hosted CI remain pending.

### Implemented in the current tree

- **Passphrase-protected invoice creation/opening and seller vault.** `CreateInvoice.tsx` creates `A256GCM-PW` links with confirmation and guidance; `Pay.tsx` prompts to unlock and does not treat the clear header as authenticated. `SellerKeys.tsx` saves/loads an encrypted IndexedDB keystore; `Sweep.tsx` requires the vault passphrase for every sweep action. `App.tsx` locks the session on idle. Evidence includes invoice/passphrase tests, `keyVault.test.ts`, SellerKeys/Sweep/session tests and `apps/web/e2e/passphrase-vault.spec.ts` (browser rerun remains pending).
- **QR display and limited camera import.** `QrFrame` is wired in `CreateInvoice.tsx`, `SellerKeys.tsx`, and `features/btc/BtcView.tsx`. Opt-in `CameraImporter` is wired in `Sweep.tsx` and `BtcView.tsx`; `apps/web/public/_headers` allows same-origin camera access. This is not yet a cross-screen QR exchange: Pay receipt QR import, seller key/device exchange, Settings, and Registry do not have corresponding QR import/export flows, and camera support is limited to the two stated screens.
- **Seller-signed receipt issuance.** `Scan.tsx` mounts `ReceiptPanel` only for an eligible verified match with current seller signer keys and transaction hash. `lib/receipts.ts` provides strict canonical encoding, domain-separated signing, and signature verification; the panel can copy/download/print the signed receipt. The digest is seller-supplied and explicitly labeled “not matched”; issuance alone does not create a durable seller-side reconciliation ledger or independently prove payment.
- **Pay-side seller-receipt import and invoice binding.** `Pay.tsx` accepts bounded JSON, validates the signature and expected invoice/payment fields, and guards races when the open invoice or trust key changes during asynchronous file reading. Focused related tests passed 86/86, `payExec` follow-up passed 17/17, and typecheck/scoped lint passed. Independent audit 21 passed 86/86 and closed the cross-invoice prepared-payment and stale receipt-import race findings. This establishes a signed seller-key attestation and field consistency only, not independent on-chain proof. The fresh browser rerun passed 17/17 in 2.1 minutes; candidate full web coverage remains pending.
- **Settings localization.** `I18nProvider` is mounted; Settings has a language picker and catalog-backed labels with English fallback and document `lang`/`dir` updates. Other production screens remain hard-coded English. Spanish/Japanese/Arabic catalogs are machine-drafted and require native-speaker review.

### Confirmed missing product flows

1. **Durable seller-side reconciliation ledger — highest-priority next implementation.** `Pay.tsx` now imports bounded seller receipt JSON, verifies its signature and binds invoice digest, chain, asset, amount, and available transaction/recipient facts to the open invoice/payment. A revision/session guard discards results if the invoice or trusted signer changes while the file is read. The focused Pay receipt suite passed 86 tests, `payExec` follow-up passed 17/17, and web typecheck/scoped lint passed. Independent security review 21 passed 86/86 and closed the stale cross-invoice prepared-payment and receipt-import race findings. The fresh signed-fixture Playwright run passed 17/17 in 2.1 minutes; full web coverage and candidate hosted CI remain pending. A seller signature proves key control and field consistency, not payment on-chain. `Scan.tsx` displays verified matches and can issue receipts, but there is no durable, searchable ledger linking invoices to scan matches and receipts across reloads. Implement a local ledger with explicit export/delete/privacy controls, linking only payment evidence already marked verified by the scan path. Candidate ownership: `apps/web/src/views/Scan.tsx`, `apps/web/src/lib/scanClient.ts`, and a new store/helper with dedicated tests; never treat a seller receipt alone as payment evidence.
2. **QR exchange beyond current screens.** `CameraImporter` remains wired only into Sweep and BTC, and `QrFrame` renders in invoice creation, SellerKeys and BTC. Pay receipt import currently accepts bounded JSON file input; it does not encode/decode receipts as QR. Settings device pairing/import and Registry QR exchange are also absent. These require explicit data schemas, parsing, sensitivity disclosures and lifecycle handling before camera input is enabled in those screens.
3. **Localization across the application.** Current `useI18n` wiring is limited to Settings/LanguagePicker; invoice, payment, scan, seller keys, sweep, registry, BTC and shared security disclosures remain English literals. Supplied catalogs do not yet cover these screen strings; native review is also outstanding.
4. **Policy-account/scheme-2 end-to-end path.** `packages/policy-scheme` contains derivation logic and the contracts include policy-account support, but `apps/web/src` has no scheme-2 create/pay/withdraw path and the standard router/scanner path remains scheme 1. Keep these contracts/packages explicitly experimental until UI, scanner, recovery, vectors, tests and deployment/readback support are designed and validated. This is a larger protocol/product decision than local ledger work.

The completion-plan percentage is an older estimate, not a current completeness measure. Passphrase invoice/vault flows, basic QR output, limited Sweep/BTC camera import, Settings localization, seller receipt issuance, and Pay-side receipt import/binding have been implemented. The remaining list above describes current screen-level and persistence gaps; it does not treat a signed receipt as independent proof of payment. External deployment/feed/key-custody requirements remain separate gates, not missing code features.

## Evidence standard for closing an item

For each gate, record the final commit SHA, relevant implementation/test paths, command and result, skipped or unavailable coverage, and reviewer/owner where applicable. For security fixes, preserve a regression that exercises the reported exploit mechanism. For deployment or external gates, link verifiable chain/release/audit evidence. Do not infer closure from ancestry, merged filenames, green partial jobs, or a report written against an older snapshot.
