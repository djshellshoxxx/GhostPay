## Current product-code gaps (highest-priority inventory)

Static scan and wiring inspection of `apps/` and first-party production `packages/` found these concrete absent flows. They are implementation gaps, not credential or deployment prerequisites:

1. **Policy-account/scheme-2 end-to-end path.** `packages/policy-scheme/src/derive.ts` and its vectors implement client derivation, and `GhostPayPolicyRouter`/`PolicyAccount` exist, but the web app has no policy-account create/pay/withdraw flow, no scheme-2 scanner integration, and normal `GhostPayRouter` still announces scheme 1. There are no imports of `@ghostpay/policy-scheme` in `apps/web/src`; `apps/web/src/lib/scanClient.ts` uses the ordinary scanner. See audit 01 C-18/K-08 and `packages/policy-scheme/DEVIATIONS.md`. Keep policy accounts explicitly experimental until an end-to-end path, recovery decision, vectors, tests and deployment/manifest support exist.
2. **Passphrase-protected invoice creation and payment, plus persistent seller-key unlocking.** `invoice-schema` supports `A256GCM-PW`, and seller key backup/import UI exists, but `CreateInvoice.tsx` only passes a boolean `encrypt` field (lines 32, 54–68) and `Pay.tsx` calls `parseFragment` without a passphrase (line 66), so there is no user path to create or open passphrase-protected links. `SellerKeys.tsx` says keys stay in memory (lines 102–104); no encrypted IndexedDB vault, idle unlock, or passphrase step-up guards a sweep. Keep these distinct from the implemented standalone keystore and envelope crypto.
3. **QR/camera user flows across screens.** `QrFrame.tsx` is implemented and tested, but production views do not import it; current QR rendering is the older `QrView` used for the invoice link (`CreateInvoice.tsx`) and Bitcoin payment URI (`features/btc/BtcView.tsx`). There is no camera decoder/import flow, and the app’s security headers explicitly set `Permissions-Policy: camera=()` (`apps/web/src/scanBundle.test.ts` fixture; deployed headers in `apps/web/public/_headers`). Thus SellerKeys, Pay, Sweep, Settings/device exchange, Registry and receipt flows cannot complete the planned QR exchange. The reusable QR component/library is present; screen wiring and opt-in camera handling are missing.
4. **Seller-verifiable receipts and invoice reconciliation.** `apps/web/src/lib/payExec.ts` creates only a payer-side `ghostpay-local-receipt` JSON object (lines 172–207); the current UI offers a local download. There is no receipt signed by the seller’s invoice-signing key, seller import/verification/reconciliation flow, or bill/print workflow. Scan data has invoice nonce available, but no UI reconciliation by nonce/amount/window was found. A local transaction receipt and scan verification are partial foundations, not the signed proof/matching feature.
5. **Localization beyond Settings.** The app provider and Settings language picker are now wired, and Settings uses the supplied English/Spanish/Japanese/Arabic keys. Other production views/components remain hard-coded English; they do not yet call `useI18n`/`t`/`Trans`. Catalog/native review remains incomplete, so Settings integration does not complete application localization.

The plan is partly stale: QR rendering (`QrFrame`), i18n infrastructure, local payer receipt export, and the encrypted keystore file export/import have since been implemented. They are not equivalent to the missing screen-level flows above. Current `FEEDS` and deployment manifests remain empty/unverified, but their verified chain data, funded deployment keys, release key and external deployment work are separate external readiness gates, not code features to fabricate in this scan. The user-selected ext6/ext7/ext8 side-branch package sources have now been imported; their test completion does not establish web/relayer integration, chain readiness, or production security.
