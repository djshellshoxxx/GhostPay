## Getting started and access

No verified public deployment URL is available from this draft. To evaluate locally, obtain the repository at the exact candidate SHA, install Node.js 22 or newer, run `npm ci --ignore-scripts` and `npm run build:libs`, then follow the [Pages build and local-serve instructions](https://github.com/djshellshoxxx/GhostPay/blob/ac08062ec540d429a0bfb24f3aab042be5d212eb/docs/pages/README.md). Local development/test builds must be marked `GHOSTPAY_PAGES_DEV=1` where the build requires it; that flag does not constitute release verification. Do not infer a deployable artifact from a successful local demo.

Use a current browser with JavaScript enabled. On a shared `*.github.io` account origin, other sites belonging to that account may share origin-scoped browser storage and scripting privileges. A dedicated origin is a required owner decision before a meaningful beta involving keys or payments. There is no browser extension or native installation requirement for the static client.

## Common workflows (test-only, when supported and enabled)

1. **Seller keys and backup:** generate or import keys; keep the encrypted keystore and its passphrase safely and separately. A download prompt alone does **not** establish that a usable backup was saved or restored. The verified-backup gate correction is included in the tested but unmerged [#175 Pages stack](https://github.com/djshellshoxxx/GhostPay/pull/175): an unverified download does not qualify as a recoverable backup. This branch-specific test result does **not** constitute independent security review, external-wallet qualification or release approval.
2. **Invoice:** select an allowed EVM test network and asset, review amount, expiry, fee, recipient and signer identity, then retain the original signed invoice. A QR or screenshot may not hold the complete verifiable document.
3. **Buyer:** import the signed invoice, confirm network/asset/amount and wallet context, review the transaction and separately authorize it in the wallet. A broadcast attempt is not confirmation; uncertain outcomes must be reconciled before any retry.
4. **Scan and reconcile:** inspect discovered stealth-payment candidates against chain evidence, confirmation/finality and invoice bindings. The optional automatic scan is opt-in, operates while the tab is visible and can expose timing and account queries to the chosen RPC provider. The separate **opt-in same-token transfer count** is an advisory, locally computed estimate of similarly sized public ERC-20 transfers—not a measure of guaranteed anonymity, an invoice match or proof of settlement. It depends on the chosen RPC's response integrity; [draft #159](https://github.com/djshellshoxxx/GhostPay/pull/159) verified a failing regression for off-filter RPC responses in [application CI 43654978311](https://github.com/djshellshoxxx/GhostPay/actions/runs/43654978311). The fail-closed browser guard at `7b6c4983e5c0ba048edf97aaff7399bd77980234` **passed corrected-head [application CI 43659189683](https://github.com/djshellshoxxx/GhostPay/actions/runs/43659189683)**; it also appears in the independently tested, **unmerged** [#161 combined draft](https://github.com/djshellshoxxx/GhostPay/pull/161). It remains outside owner #157 and is not release-approved.

   **Automatic invoice matching is a local suggestion, not payment proof.** For fixed-token invoices, the client compares a verified router observation with the registered invoice’s network, asset, expected net amount and observation time. A unique match can be labelled exact *within the supplied local records*; competing invoices/payments and observations first recorded after expiry are treated as ambiguous. The chain carries no invoice reference, and even an exact suggestion does not replace independent settlement/finality checks. Imported history, invalidated observations and seller-issued receipts are not automatically treated as current payment evidence.
5. **Receipt and recovery:** retain signed receipts **and** actual chain settlement evidence. A seller signature alone does not prove settlement. Native-coin testnet sweep/recovery is represented in the draft's local-chain acceptance; ERC-20 sweep needs externally provided gas and is **not qualified by that devnet acceptance**.
6. **QR and imports:** use the documented invoice/payment-request/receipt/backup formats only; import must validate sizes, integrity and network identity. Do not treat QR payloads as implicit transaction authorization.

## Encrypted reconciliation, local invoice links and historical backups

**Status:** The encrypted reconciliation UI from [draft #172](https://github.com/djshellshoxxx/GhostPay/pull/172) is carried into the newer tested but **unmerged** [draft #175](https://github.com/djshellshoxxx/GhostPay/pull/175) Pages stack, including the historical-import verification-label correction from #173/#175. It is not a hosted bookkeeping service, wallet transaction verifier or publicly released product.

In the **Scan** view, unlock the reconciliation vault for the current seller key and network. Only a matching router-verified scan observation with parsed metadata and a transaction hash can be saved as a new local payment observation. An optional invoice digest is a **manual annotation**, not cryptographic payment-to-invoice evidence. A locally suggested exact match requires an explicit confirmation; when invoices or payments compete or observation is late, matching is marked ambiguous rather than confirmed automatically.

The browser keeps current reconciliation records, registered invoice annotations and archived receipts encrypted in the seller/network-scoped IndexedDB vault. **Export encrypted reconciliation backup** produces a separate file. To restore, enter or select that encrypted file, choose **Preview encrypted backup**, review counts and possible reorg-invalidated records, and then explicitly **Activate previewed historical records**. Imported observations remain historical/untrusted; importing them does not revalidate chain finality, recreate a missing live scan, confirm invoice settlement or authorize a sweep.

Old **legacy plaintext reconciliation data** is a separate untrusted migration surface: the UI permits reading it, explicitly consenting to a plaintext export, or deleting it. It cannot enable new plaintext writes or automatically turn those records into current payment evidence. Treat plaintext exports as sensitive.

**Status-label qualification:** Source review of #172 found that an imported historical observation bearing an invoice annotation could be labelled “linked to a verified observation” in the invoice registry despite retaining imported provenance. A minimal browser-only correction and regression are proposed in isolated [draft #173](https://github.com/djshellshoxxx/GhostPay/pull/173) at `97cf5a0cda257451c99643909a7b5ebe7da89a79`; **fresh exact-head CI is pending**, and the fix is **not merged** into #172. Until integrated, use current chain evidence and the record's provenance/invalidation label rather than relying on the invoice-registry linked summary for historical imports.

## About, privacy and chain-fee disclosures

The lean Pages client's **About and privacy** view explains which parties can observe payment metadata, what stealth addresses cannot hide, and how to verify release provenance. The observer table includes a *relayer operator* as a general threat-model category; that row does **not** mean a GhostPay relayer service runs behind the Pages client. Invoice links remain bearer secrets, the host and selected RPC can observe metadata, and using a familiar wallet as the sweep destination makes the public transfer linkable.

The per-chain fee panel reads the checkout fee from the chain-adapter fee schedule and displays router/fee-recipient addresses only when that chain's deployment manifest has loaded. When the manifest is absent, invalid or rejected, the panel reports **payments disabled** rather than presenting an assumed fee recipient; a loaded manifest alone does not substitute for independently verifying a trusted signed manifest and on-chain contract. **Traceability:** [About.tsx](https://github.com/djshellshoxxx/GhostPay/blob/dffe072511c34b8a73bd64ac6147d5a79256480e/apps/web/src/views/About.tsx), [Disclosure.tsx](https://github.com/djshellshoxxx/GhostPay/blob/dffe072511c34b8a73bd64ac6147d5a79256480e/apps/web/src/components/Disclosure.tsx), [About.test.tsx](https://github.com/djshellshoxxx/GhostPay/blob/dffe072511c34b8a73bd64ac6147d5a79256480e/apps/web/src/views/About.test.tsx) on exact unmerged #172. ## Troubleshooting and FAQ

- **Why are payments disabled?** No approved signed testnet manifest was bundled, the selected wallet/network does not match, or a fail-closed check prevented operation. Do not circumvent deployment trust pins.
- **Why is a payment pending or failed?** Check wallet rejection, RPC results, transaction hash, chain and finality. Timeouts do not prove that no transaction was broadcast.
- **Why is another wallet send blocked after an uncertain result?** The Pages client records an attempted wallet handoff in this browser tab before submitting it, even if the wallet returns no hash. The record is **tab-scoped session storage**, not a permanent, cross-tab transaction ledger or proof of settlement; closing the tab or opening another may not preserve the same record. Do not clear it or retry because a timeout, tab closure or missing hash looks like failure. First independently check the wallet and the selected chain for the earlier transaction, and retain its hash and receipt where available. Clearing a record requires confirmation and cannot undo a broadcast.
- **Why is a receipt rejected?** Confirm the original signed invoice, signer pin, chain, token, amount, recipient, actual transaction and finality. A receipt alone does not certify chain settlement.
- **Can I restore keys after clearing my browser?** Only with a complete externally saved encrypted backup and the correct passphrase; local storage is not custodial recovery. The independent backup-verification fix remains under review.
- **Does inactivity automatically secure the wallet?** The device-sleep idle-lock behaviour (GP-PAGES-04) remains an open candidate correction on this head; do not rely on it as a fully qualified defense.
- **Is it anonymous?** No. RPC queries, wallets, transaction senders, timing, amounts, approvals and subsequent sweeps can expose linkage.
- **Can I run the CLI, relayer, BTC or other chain apps from Pages?** No. Those are preserved separately and are excluded from active Pages development.

## Privacy, security and safe use

This is **pre-audit** software. Protect secret keys and invoice capability URLs; browser fragments and browser extensions can expose sensitive data. Selected RPC providers see network metadata and requests, and a static host cannot supply response security headers such as `frame-ancestors`. A self-displayed file hash is for comparison with independently obtained release evidence, not a proof of host integrity. The build may execute only approved testnet operations after separate configuration and review; no real funds, mainnet, release or public deployment are authorized. Consult [SECURITY.md](https://github.com/djshellshoxxx/GhostPay/blob/ac08062ec540d429a0bfb24f3aab042be5d212eb/SECURITY.md) for private security reporting and the [Pages guide](https://github.com/djshellshoxxx/GhostPay/blob/ac08062ec540d429a0bfb24f3aab042be5d212eb/docs/pages/README.md) for current limitations.
