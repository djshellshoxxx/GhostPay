### Recovery audit of #260 against #239/#240

The review traced [portable export codec](https://github.com/djshellshoxxx/GhostPay/blob/f3bb7c662274c4a4394324c405b49517ad2b1461/packages/ux-vault/src/stealth-export-portable.ts), [browser orchestration](https://github.com/djshellshoxxx/GhostPay/blob/f3bb7c662274c4a4394324c405b49517ad2b1461/apps/web/src/lib/paymentKeyExport.ts), session installation, recovery/verification components and AppShell unload protection.

No new scoped source blocker was found in the audited paths:

- A payment export derives the one-time key, independently recomputes its address, validates the public point/address and checks each decrypted private scalar against its record. The authenticated header binds public metadata, format, KDF and cipher parameters.
- The decoder bounds input before parsing, rejects duplicate JSON keys/non-ASCII, validates exact ciphertext and canonical plaintext lengths, and disposes rejected secret buffers. The browser additionally compares original `File.size` with the ASCII text length, preventing `File.text()` from certifying a BOM-altered saved file.
- #239’s atomic replacement stages the entire new wallet before clearing the old one and disposes partial allocations on failure. Generated-ciphertext retry and verification-state invalidation remain present.
- #240’s unload rule reads live session/external-copy state at the event. A cached browser-local vault does not suppress protection, and master payment-key recovery does not falsely certify the separately generated invoice-signing key.

The existing session-lifecycle work remains a composition requirement. At #260, idle handling notifies views and waits for custody without first suspending ordinary key authority.
