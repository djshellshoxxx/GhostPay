## Remaining requirement scope

This generation does **not** close issue #287 item 4. It provides no persistent transaction/invoice metadata retention and no terminal-transaction presentation adapter. Existing stored records cannot be automatically classified as nonessential from age, status name, a returned hash or a receipt signature.

A new bounded adapter must first identify a real field or presentation copy, prove that it carries no recovery/duplicate/trust/reorg evidence or sole-copy record, define current-session eligibility, and bind preview/confirmation to the exact record revision inside its storage transaction. Unknown or changed records stay protected. Do not create a sensitive collection merely to demonstrate cleanup.

A lower-risk next integration is the existing merchant invoice **screen result**, after the coordinator merges the merchant minimization branch. It can reuse the current preview adapter while preserving the signed profile, editable settings, pending generation guards and separately saved registrations. That still would not establish persistent-data requirement completion.
