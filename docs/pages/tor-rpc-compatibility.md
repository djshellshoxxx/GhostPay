# Pages HTTPS, Tor and RPC compatibility

Scope: the lean EVM Pages client at `f76904301cff0b24d65ea4e31cbf37d470db4d95`. Opening a signed invoice and submitting a payment have different network requirements. A fresh browser can load, create and review invoices from the static site alone. Chain operations require an explicitly configured provider and a verified deployment. A buyer also needs a compatible wallet to authorize a transaction.

| Connection | When it occurs | What the operator can observe or influence |
| --- | --- | --- |
| Static HTTPS origin, or an operator's separately hosted onion mirror | Initial document, bundled JS/CSS, local icons/help, lazy assets and workers as needed. Home also reads its own entry bundle to display a hash. | File paths, timing and connecting address. An invoice fragment stays in the browser. The host controls the delivered code. An in-app hash cannot authenticate a compromised host. Sites under one GitHub Pages account share an origin. |

## Routing and failure behavior

- **Direct** uses the configured scan endpoint or the per-chain Settings RPC. The normal client verifies `eth_chainId`; a wrong chain is refused. Some transient errors are retried on the same endpoint. A second provider is a cross-check, not automatic failover. Failure to read a receipt leaves settlement uncertain.
- **Tor Browser** records the user's selected scan mode. The page uses the browser's ambient networking. It cannot start Tor, check a circuit or detect direct routing. With no scan override, this mode uses Settings RPC and can also use a configured second RPC. Choosing the setting in ordinary Chromium still uses Chromium's route.
- **Local proxy** takes a loopback HTTP(S) **JSON-RPC forwarder**, not a SOCKS port. A missing or failed proxy blocks the scan. The page cannot verify the forwarder's upstream. A required proxy protects the scan path. Settings tests and other actions have their own network paths. Endpoint URLs, including any project key in a path or query, are stored in plaintext browser preferences.
- The host, RPC and wallet are independent trust decisions. A clearnet HTTPS endpoint reached through Tor can see the exit address, request details and timing. An onion service has no exit hop. Hosting the files on an onion service alone says nothing about a wallet's route or on-chain linkability.

## Documentation discrepancies on the reviewed commit

| Published wording | Observed implementation and operator consequence |
| --- | --- |
| Pages setup and the user privacy guide suggest HTTPS or WSS for the primary RPC. | Settings accepts WSS syntax. The default web service calls `createClient` with the HTTP fetch transport, which rejects WSS. Supply HTTPS for a working EVM primary. CSP permission for WSS does not provide a WebSocket client. |
| Pages setup presents HTTP loopback as a working scan proxy on the mirror. | The scan URL validator accepts loopback HTTP. The shipped meta CSP permits connections to self, HTTPS and WSS. From a distinct HTTPS Pages origin, cross-origin plain HTTP is outside that policy. Use a trusted TLS loopback forwarder with suitable CORS for this profile. |
| Pages setup says the scan blocks when a required Tor Browser path is unavailable. | Selecting Direct with a required private path blocks, as does a missing local proxy. Selecting Tor Browser can proceed in an ordinary browser. It is a declaration, not a route check. |
| The privacy guide says the scanning page has no network access. The bundled privacy page describes a second RPC as adding availability. | The matching worker handles the viewing key locally. The page fetches logs and can request receipts identifying matches. Requiring a second provider adds a verification dependency and can reduce availability. |
| The user guide describes fixed scan windows as off by default. | The initial transport is Direct and jitter is zero. The default scan window is 1,000 blocks, capped to the chain's supported log range. |

## Browser and release boundaries

Interactive use requires JavaScript, a secure context with Web Crypto and relevant storage/worker support. Local static help and privacy pages remain readable with JavaScript disabled. Private browsing, clearing site data and Tor Browser's New Identity can discard local state. Keep a verified backup outside the browser. No stock Tor Browser wallet or external-wallet proxy configuration is assumed. Tor Browser's Standard level enables JavaScript by default; higher levels can restrict site features. [Tor Browser security levels](https://support.torproject.org/tor-browser/features/security-levels/) · [Onion services](https://support.torproject.org/tor-browser/features/onion-services/)

The existing Tor hosting and live acceptance work is tracked in [PR #363](https://github.com/djshellshoxxx/GhostPay/pull/363), with a save-confirmation fixture in [PR #436](https://github.com/djshellshoxxx/GhostPay/pull/436). The live plan gates Tor bootstrap, disposable onion descriptor publication and workflow dispatch. Offline Chromium, native-fetch checks and a saved preference do not qualify real onion reachability, browser-wide egress, wallet routing, mainnet or settlement. The broader network-isolation owners retain their policy, source and release gates.
