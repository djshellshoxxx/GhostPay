# Network, privacy and exchange source review

## Status and method

This is a source-only defensive review of the `network-privacy-exchange` domain in `source-inventory.json`. The authoritative inventory contains 116 distinct `(path, blob)` versions across the eight commits in `scope-refs.json`. `network-privacy-coverage.json` records the exact versions read, their source aliases, and any remaining work. A `reviewed` row means the complete source was read and analyzed, or a previously read full baseline was followed by its complete source diff. A source-search hit alone does not earn coverage.

**Pinned domain coverage is complete: 116 of 116 versions across 108 paths.** The first reviewer completed 94 versions; the successor completed the remaining 22 net-transport versions by reading 19 complete baseline sources and all three complete release diffs. The two previously completed net-transport versions remain unchanged. Completion applies only to the eight pinned snapshots; subsequent moving-head changes remain a separate coordinator review.

The package inventory is broader than the set of functions actually called by the browser: exports are examined, but an unused helper is not assumed to be a reachable browser vulnerability. In particular, recent browser code imports `padBody` from metadata-hardening and `DestLedger`/`fundingGuard` from hygiene; other helpers require separate consumer evidence before being characterized as active browser paths.

No code changes, exploit scripts, reproduction attempts, live requests, broadcasts, deployments, or vulnerability tests were performed by this worker. Existing test sources can describe intended behavior; their presence does not establish a passing execution. GitHub publication was previously blocked by automatic approval review and was not retried.

## Confirmed issues

### NPE-01 — Rejected multipart conflicts extend the QR import idle deadline

**Severity:** Low. **Confidence:** High from source. **Status:** Already-known defect, fixed in one selected candidate line; not a new independent discovery.

**Evidence:** On main `c977b5d6723f6822c3b5d86cd6b231712c53c395`, `packages/qr-exchange/src/assembler.ts:63–87` (blob `8e8d12e447265e682597edf2887e5a2f6afd55db`), `add()` evaluates session expiry, then updates `#lastActivity` at line 78 before it detects and rejects a same-index conflicting chunk at lines 79–85. The rejected input therefore still changes the session's expiry state.

**Preconditions:** An incomplete multipart import is in progress, and a same-session chunk conflicts with an already held part while remaining within the current idle period. The input is rejected, but its arrival changes the idle timestamp.

**Actual impact:** The stale import can remain alive beyond the intended period without accepting replacement content. This is an availability and session-lifetime defect. The reviewed code still rejects the conflicting bytes and checks complete-payload integrity; this review does not claim an authentication bypass, secret disclosure, or successful payload substitution.

**Affected selected snapshots:** main, release, privacy-snapshot, quick-hide, clipboard, erc20-simulation. All contain the old blob above.

**Fixed selected snapshots:** consolidation `e22c1748a3de6eb02f5be3abe27d634b238c67c6` and format `a9e0715573f7247d7a16f9d1d030cf0232708fb2` contain blob `144dd8ec67e8aaeffc5c3d90f6a06234d770abcd`. Their lines 78–86 perform conflict rejection before updating the activity timestamp. The existing repair commit is `118ae827a5244156226c48e7d4cc3eb3524810ff` (`fix(qr-exchange): preserve idle deadline on rejected conflicts`).

**Remediation:** Integrate the existing focused fix through the normal reviewed branch workflow. Preserve the requirement that rejected chunks leave the session deadline unchanged.

**Benign regression guidance:** With a synthetic clock and ordinary in-memory chunk fixtures, assert that an accepted part updates the idle timestamp, a rejected conflict does not, and expiry remains measured from the last accepted activity. Retain session mismatch, payload hash, size, chunk-count and reset coverage. No regression was executed in this audit worker.

### NPE-02 — Unbounded indexer URL normalization retains excessive synchronous work

**Severity:** Low, availability. **Confidence:** High in the source defect and current caller path; no runtime timing measurement. **Status:** Remaining instance of a previously recognized URL-normalization defect family.

**Evidence:** In all eight selected snapshots, `packages/scan-source/src/indexer.ts:66–75` (blob `c4f85a42d17c6661792cf45f10aff391074823a3`) accepts an unbounded base URL and removes terminal slashes with an unanchored repeated-match regular expression. In backtracking implementations, unsuccessful suffix searches can repeatedly rescan the path. This work occurs synchronously while constructing the source, before the transport's timeout or response limits can apply.

The browser reaches this constructor in main `apps/web/src/lib/scanPrivacy.ts:573–583`, and release `417f7c71daf8645e1432f2ec8f070110879b80bd`, `apps/web/src/lib/scanPrivacy.ts:640–650`. The shared browser URL checker already uses a linear terminal walk (main lines 85–98; release lines 122–135), but does not impose an input-length bound. Release `apps/web/src/views/Settings.tsx:621–623,675–677` accepts the user-configured indexer URL without a field length limit. The lower package therefore reintroduces the work avoided by the browser checker.

**Preconditions:** The user selects the indexer scan path and accepts an unusually long indexer URL, or already has such a value in local scan settings. An ordinary remote RPC response alone does not control this value. This is not characterized as a remotely triggerable issue without configuration influence.

**Actual impact:** Building the configured indexer client can consume excessive synchronous CPU and stall the page. No disclosure, payment authorization bypass or funds movement was established. Duration depends on the input and JavaScript engine; this audit did not run a timing or denial-of-service reproduction.

**Branch status:** The indexer source blob is unchanged across all eight snapshots. A parallel instance in `packages/pir-two-server/src/client.ts:79` on main/erc20-simulation was already replaced with a linear terminal walk in the other six selected snapshots by commit `d37b0ab37d0e9968bda21c57bd18d78c2897487d`. That PIR fix does not change the indexer constructor. PIR is an experimental library path, not an offered current browser scan mode.

**Remediation:** Apply the existing linear suffix-removal approach to the indexer constructor and place a documented URL-length budget at both the package input boundary and browser settings validation. Preserve valid origin/path bytes and existing scheme, credential, query and fragment restrictions.

**Benign regression guidance:** Check ordinary root and nested-path URLs, terminal slash normalization, and maximum accepted URL length. Assert rejection above the budget before invoking downstream construction. Prefer a structural bounded-work assertion over a flaky wall-clock threshold. No test was executed by this worker.

### Informational transport API limitation — OHTTP's deadline depends on cooperative operations

**Disposition:** Informational API contract limitation, with high confidence from source. This is not an additional demonstrated current Pages vulnerability. The browser entry does not export the OHTTP factory, the selected browser imports use that entry, and no inventoried browser/dependency consumer of this factory was found.

**Evidence:** In every pinned snapshot, `packages/net-transport/src/profiles.ts:492–532` (blob `1549e1d6ce45263576f1aef5c3fbe699258dd64c`) implements the OHTTP request timer by calling `ctl.abort()` at lines 495–498. It then awaits the injected HPKE encapsulation, relay POST and response decapsulation at lines 514, 517 and 526 without a rejecting deadline race. The HPKE interface does not take this signal. The underlying transport contract requires enforcement of `timeoutMs` (`packages/chain-adapters/src/rpc.ts:34–40`). The existing OHTTP timeout fixture at `packages/net-transport/src/ohttp.test.ts:318–328` supplies a relay callback that explicitly rejects on abort; it was inspected, not executed.

**Preconditions and actual limit:** A library caller explicitly enables the experimental OHTTP profile and supplies an HPKE implementation, or a custom relay callback, whose operation remains pending. The controller deadline alone cannot settle that awaited operation, so the returned request promise can remain pending beyond the advertised timeout. Default native-fetch network work receives the abort signal; this observation does not establish that an ordinary remote response defeats native fetch cancellation. No direct fallback, cryptographic break, disclosure or active-browser availability impact was established.

**Remediation and benign regression guidance:** Before considering this profile for supported use, apply a rejecting overall deadline across encapsulation, relay I/O and decapsulation, check expiry before starting each later phase, and retain best-effort cleanup without making it a settlement prerequisite. Controlled held promises and a synthetic clock can check bounded rejection and refusal of late results without network access. Actual HPKE correctness and protocol-vector qualification remain separate. No reproduction or regression was run here.

## Completed transport boundary analysis

- **Current browser fetch path:** Main reaches `createFetchTransport` through `apps/web/src/lib/scanPrivacy.ts:634–653`; release reaches it through `apps/web/src/lib/defaultServices.ts:91–111` and `scanPrivacy.ts:704–724`. The transport validates positive, representable time and byte budgets before dispatch (`fetchTransport.ts:38–44`), sets redirect refusal, omitted credentials, no-store and no-referrer options (`59–68`), bounds streamed bytes and rejects late results (`69–99`), and races the full fetch/read operation against a deadline (`110–124`). Only errors constructed within that request preserve their detailed codes; injected fetch/stream errors become a fixed failure. The same transport blob appears in all eight snapshots. No additional current-browser defect was established in this package boundary.
- **Cancellation and adapters:** `fetchAdapter.ts:27–52` handles explicit POST bodies, Request/init signal inheritance, pre-dispatch cancellation, prompt cancellation rejection and listener cleanup. The `RpcTransport` interface has no request signal, so cancellation after dispatch cannot recall sent bytes or itself stop the inner operation. The code documents that limit. Full source of `fetchIsolation.test.ts` and `fetchAdapter.isolation.test.ts` was read as contract evidence, not run.
- **Node proxy paths:** The complete proxy URL, SOCKS negotiation, HTTP CONNECT, socket-reader and tunneled-request sources were read. Profile construction restricts proxy endpoints to IP literals or mapped localhost by default; destination names are encoded for the proxy. Credentialed SOCKS negotiation offers only its required authentication method, so this handshake cannot silently downgrade to no-auth. Internal response statuses and connection errors are bounded or sanitized. These factories are outside the selected browser entry; this review does not qualify real Tor, I2P, Nym, DNS routing or TLS interoperability.
- **Profile truthfulness and cryptography:** Direct and Tor-browser profiles make no programmatic privacy claims; Tor-browser depends on the user's browser choice. Recent labels explicitly mark overlay profiles unverified. The testnet guard constrains declared configuration, rather than proving an endpoint's actual chain or honesty. OHTTP validates framing, key-config sizes, offered suites and configured target origin, while encryption, randomness and authentication are delegated to injected HPKE. No real HPKE implementation, RFC vectors or overlay network was qualified. Different relay/gateway origins and the last-two-labels check remain configuration checks and heuristics, not proof of independent operators.

## Review observations, without an additional vulnerability claim

- **Address and transaction review:** Strict address/checksum and token handling, sanitized display text, canonical calldata re-encoding, closed selectors/types, independent expected-intent comparison, and explicit policy checks were read. Advisory fingerprints and trust labels do not replace transaction authorization. A runtime programming-shape error can make some typed helpers throw; that alone is not evidence that an untrusted request can pass authorization.
- **Payment URIs:** The parsers use bounded strings, exact bigint amounts, strict percent decoding, duplicate-key rejection, network/chain checks and display-text sanitation. The Lightning field and silent-payment address parser explicitly do not authenticate or send a payment; later consumers remain responsible for their full protocol validation.
- **QR exchange:** Chunk count, text and payload size are bounded. CRC and truncated digest fields are described as transport-corruption checks, not authentication. Public seller pairing requires independent confirmation, and settings transfer validates selected public sections without applying them or fetching URLs. Image pre-decode dimension checks cover the named PNG/GIF/JPEG/WebP formats; other raster formats have a post-decode pixel check. No additional confirmed current-browser security defect was established in those paths.
- **Metadata hardening:** Source was read for amount/gas rounding, padding, deterministic derivation, view-tag modes, endpoint separation, scan ranges, release scheduling, Bitcoin helper policies, and the catalogue's privacy limits. Metadata reduction is explicitly limited; it does not establish anonymity, RPC honesty or independence of operators. No distinct active-browser defect was established by this worker.
- **Hygiene:** Source was read for derivation and secret disposal, ledger invariants, address-free request construction, decoy selection, funding and consolidation checks, and rounding. Address-free verification helpers still trust their RPC result source; their returned log observations are not a consensus proof. The selected browser consumers of the package are ledger and funding helpers, so unused verification utilities were not promoted to reachable browser findings.
- **PIR and scan sources:** Full PIR source and its recent URL-normalization diff were read, followed by every scan-source baseline and recent padding/cancellation/opt-in change. XOR queries use fresh uniform randomness; reconstruction is checked against manifest leaves, and manifests are compared across both servers. The independent head check does not turn the database into a proof of all chain log contents, and non-collusion remains an explicit assumption. Current browser indexer wiring keeps its results unverified and later binds router payments to independently read receipts. The recent range/padded helpers stop scheduling after cancellation; a pending backend request still requires backend settlement.
