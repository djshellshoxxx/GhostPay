## Controls examined

The release workflow verifies a signed tag against default-branch-pinned trust material, checks ancestry, re-verifies after approval and binds analyzer evidence to the source commit. Release publication is a draft step with separate credentials. Missing trust roots fail closed. `verify-release.sh` checks artifact consistency; it does not claim that a hash alone authenticates its publisher.

The Pages builder checks clean source identity and stages generated artifacts in a private directory. Its artifact verifier constrains relative paths, checks regular files without following final-component symlinks, compares file identity/metadata and reuses the verified bytes when checking build metadata. Stable private ancestor directories remain an explicit assumption; the implementation is not an atomic filesystem snapshot. The attestation job obtains its narrow identity permission without checking out or executing arbitrary source, and deployment depends on that job.

The local Pages server binds loopback, allowlists served extensions and refuses hidden/symlink paths. Browser smoke scripts use read-only navigation and fixtures. Their source was read but the scripts were not run. Their checks cannot prove absence of arbitrary malicious application behavior, independent RPC routing or live-chain correctness.

Embed v1/v2 use constrained same-origin messages, source/nonce checks, text rendering and appropriate popup isolation. Their completion event means submission, not settlement. Shared-origin applications can share browser security/storage authority; a subpath does not create an independent origin. Lean builds exclude the full embed surface where specified by the profile.

All original i18n code and every security-key classification variant were read. Unknown security-sensitive keys fall back to reviewed/source text; only the neutral-key list permits unreviewed translation. Catalogs are bundled inputs, message formatting produces React text/controlled rich text, and styles did not contain an additional network disclosure path. Static translation catalogs were not exhaustively copyedited. The complete classification file was read in contiguous sections; its size was not used to waive review.

The inventoried IndexedDB/concurrency test-support scripts were inspected as source only. They are included in file accounting but are not evidence of executed assertions.

## Latest static Tor deployment: coordinator review

The `tor-completion` snapshot is `14a7526842b3cb055452b721d237a7e68813ff0c`. Source anchors below refer to that commit. [Pinned deployment sources](https://github.com/djshellshoxxx/GhostPay/tree/14a7526842b3cb055452b721d237a7e68813ff0c/deploy/tor-static).

`prepare.mjs:75–149` requires an operator-supplied expected archive digest, validates the onion host configuration, refuses an existing output and requires the archive's matching header policy. It verifies the digest again when generating from a fresh private copy. A temporary sibling contains generated files until rename; cleanup removes only that new stage. The output parent and templates remain trusted operator inputs. The helper does not start services or access an onion identity. As with the underlying kit, a trusted expected hash authenticates only as well as the channel that supplied it.

The final Compose override removes published host ports and the web container's egress network. The runbook requires all three Compose files in order. Omitting that explicit override is a deployment configuration change; the recipe does not silently promise that the generic two-file setup is onion-only. The generated identity volume is separate from site/build files, and the new Docker context allowlist excludes accidental identity backups. The documentation distinguishes the public hostname from the private identity and warns that deleting the named volume destroys continuity.

`Dockerfile:9–16` checks the fixed source archive hash before extracting/building Tor. The default base is digest-pinned, but distribution compiler/runtime packages are resolved at build time, so the complete image is not reproducible from source pins alone. `tor-start.sh` restricts options, checks a stable version floor and PoW/GPL reports, enforces an owned non-root mode-0700 data volume, verifies its explicit torrc and then executes Tor. No image or runtime was exercised in this audit.

The official [Tor 0.4.9.17 announcement](https://forum.torproject.org/t/security-release-0-4-9-17/22454) and [download page](https://download.torproject.org/tor/) were checked on the audit date and identify the pinned stable release. The web reader could not retrieve the upstream checksum body because it reported an unsupported content type. This audit therefore does **not** independently authenticate the exact pinned checksum or verify its upstream signature. The recipe's own runbook already records that qualification gap. No conclusion of a wrong checksum follows from unavailable retrieval.

`.github/workflows/tor-static.yml` grants read-only repository access, pins actions, disables install scripts and defines build/configuration checks without Tor bootstrap. Its container cleanup targets runner-only fixture state. `scripts/tor/browser-acceptance.mjs` blocks external requests/WebSocket attempts, checks two loopback origins and uses synthetic page state; its report expressly excludes live onion/Tor Browser/extension routing. Reading that workflow and script is not evidence that either passed.

No additional independently confirmed coordinator finding was established in these nine supplemental source versions. See the hosting module reports for their findings and hardening observations; final consolidation is in `FINDINGS.md`.
