## H-AD-01 — Raw preview error responses need a final header-value boundary

**Final classification:** Informational conditional library hardening, with Low repair priority; static data flow established, practical cross-user impact not established. Independent review confirmed that the sole production caller omits the enabling host configuration on all twelve refs; see `hosting-finding-quality-review.md`. **Affected versions:** the single `preview.mjs` blob shared by all 12 snapshots. The latest Tor origin-validation change does not alter this path.

The ordinary response writer uses `ServerResponse.setHeader`, but `sendRaw` serializes response headers itself and writes them directly to the socket. The `clientError` handler obtains a request target from `err.rawPacket` by splitting first on CRLF and then on the ASCII space character. `parserRejectReply` can preserve that target when the method passes its token check and `isBadRequestLine` does not reject it. That latter gate checks request-target shape and the routing parser's limited rejection conditions; it does not reject every raw control character. Splitting on CRLF alone does not exclude an embedded bare LF or another non-NUL control from the extracted token. [Source: `kit/serve/preview.mjs:75-76,294-310,324-334,421-426`; supporting routing boundary: `kit/serve/routing.mjs:94-97,115-127,136-140`.]

When a programmatic caller passes a clearnet `hostConfig` with `onionLocation`, `transportHeaders` appends `requestTarget` to the validated onion origin. `kitResponseHeaders` forwards the resulting value, and the raw writer performs no final header-value validation. The canonical onion-origin validation protects the origin component; it does not sanitize the appended request target. Thus the raw-error path can carry request-controlled header control characters that the ordinary Node header API would otherwise reject. [Source: `kit/serve/preview.mjs:251-256,365-385`; supporting header implementation: `kit/serve/headers.mjs:402-412,420-437`.]

**Reachability and impact limits.** The preview binds only literal loopback addresses. The actual CLI `runPreview` caller passes no `hostConfig`, so `onionLocation` is absent on that path. No other production caller enabling this option was established within the reviewed closure. A requester also needs a connection to a preview instance with that programmatic option enabled; the consequence beyond malformed response framing depends on how a downstream HTTP recipient or proxy handles controls. No browser, proxy, cache, response-splitting or cross-user exploit was reproduced or inferred as established. [Source: `kit/serve/preview.mjs:365-366,413-435`; supporting CLI call: `kit/cli.mjs:540-548`.]

**Remediation.** Treat parser-error responses as independent of the rejected request target: omit request-derived transport headers or construct them from a fixed, trusted path. Also validate all names and values immediately before raw serialization, using a single header-validation boundary shared with the ordinary writer. Reject invalid data rather than trying to repair it by deleting individual characters. A later authorized regression check should assert that raw error replies contain only valid header fields for malformed request targets and that ordinary valid Onion-Location paths remain unchanged. No such check was run here.

**Disposition for the aggregate audit:** retain as conditional library hardening. Do not promote it to a demonstrated default-CLI or deployed Tor finding, and do not attach an exploit payload.

## Security properties supported by the reviewed source

### Configuration and generated directive safety

`parseHostConfig` accepts a fixed set of keys, rejects nonplain objects and unknown trust/secret-related fields, and constructs a new normalized configuration object. TCP listeners are literal loopback addresses with unprivileged ports; Unix socket paths use a conservative bounded character set. Base paths and labels have separate restrictive validation. These are concrete checks on the public hosting configuration, not a mechanism for changing application RPCs, chain settings, signing material or contract addresses. [Source: `kit/config/host-config.mjs:12-20,35-36,150-192,200-236` at Tor completion.]

The adapter boundary additionally validates transport, listener, labels, numeric ports and absolute paths. Tor directive values do not accept whitespace, quoting or control characters through the path fields. I2P tunnel names, router-relative key paths and sanitized descriptions are checked before either renderer receives them; a final plain-value check covers the rendered string fields. Neither I2P renderer reads a key file or starts a process. [Source: `kit/adapters/tor.mjs:95-165,263-301`; `kit/adapters/i2p.mjs:94-155,171-225`; `kit/adapters/i2p-i2pd.mjs:12-41`; `kit/adapters/i2p-java.mjs:35-62`.]

The nginx profile quotes paths and values, refuses control characters and unapproved `$` interpolation, validates unquoted header-name tokens and applies the policy gate before generation. Request-dependent variables are generated internally. The programmatic low-level renderers still expect typed, validated inputs; the higher-level parser/adapter boundary is the relevant untrusted-config boundary. No CLI path bypassing that boundary was established by the inspected callers. [Source: `kit/profiles/nginx.mjs:94-110,117-132,213-218,300-328,404-425`; supporting caller: `kit/cli.mjs:622-676`.]

### Serving and origin assumptions

The preview enforces loopback binding, a listed-file router, GET/HEAD-only dispatch and response-header policy checks. Generated nginx disables autoindex and symlink following, uses relative redirects, sets request/time limits, rejects unsupported methods and adds policy headers at server scope with `always`, avoiding the location-level header-inheritance problem. These observations establish the configuration being generated; they do not revalidate nginx behavior or browser enforcement at runtime. [Source: `kit/serve/preview.mjs:55-68,204-227,265-287,365-385,413-435`; `kit/profiles/nginx.mjs:39-47,213-218,241-255,321-360`.]

Host validation is **syntactic**, not an origin allowlist: `isBadHost` and the generated `$hk_bad_host` map check header structure, and nginx uses a default server. `publicOrigin` is not compared against the incoming Host value. In the reviewed implementation, these are public static-file endpoints with no privileged mutation API, no upstream fetching and no Host-derived absolute redirect. Consequently this is not recorded as an authentication bypass, SSRF or demonstrated DNS-rebinding issue. If privileged endpoints are ever added, the present Host check must not be reused as their authorization boundary. [Source: `kit/serve/preview.mjs:84-107,265-287`; `kit/profiles/nginx.mjs:289-294,337-359`.]

### Process and identity separation

Tor and I2P profile generation returns inert file bytes. The Tor dedicated/container configuration disables SOCKS and control TCP ports, writes safe logging configuration and keeps identity data in an operator-owned directory or a separate named volume. Container profiles run nginx as uid/gid 101 with a read-only filesystem, dropped capabilities, no-new-privileges, bounded runtime storage and process/memory/CPU limits. The Tor sidecar runs as `debian-tor`, uses a separate data volume and publishes no ports in its override. These are generated defaults, not runtime observations. [Source: `kit/adapters/tor.mjs:362-432,503-561`; `kit/profiles/container.mjs:71-132,141-169`.]

I2P uses dedicated router-relative destination-key names and rejects known router-state names, traversal segments and the documented transient-key prefix. The Java renderer starts disabled until an operator enables the tunnel. The i2pd renderer requests that visitor identifier headers and per-visitor loopback mapping be disabled, and it explicitly states the older-version limitation of the header option. [Source: `kit/adapters/i2p.mjs:45-49,107-145`; `kit/adapters/i2p-java.mjs:38-60`; `kit/adapters/i2p-i2pd.mjs:24-35`.]

## Latest Tor delta

The only changed owned paths are `adapters/tor.mjs` and `config/host-config.mjs`.

1. **Shared, checksum-aware adapter validation.** The older direct Tor adapter boundary accepted a matching 56-character onion shape without verifying its checksum. The new adapter delegates to `validateOnionOrigin`, which verifies the v3 version and checksum as well as the origin form. Normal baseline CLI parsing already used the checksum validator, so the older raw-adapter behavior should not be described as a bypass of the CLI parser. [Baseline `tor.mjs` blob `0105435acbeb2a19bbf9b00564a0848846e2a60a:78,95-104,500-502`; latest `tor.mjs:95-106,503-505`; both config versions' `isValidOnionV3Label:70-79`.]

2. **Canonical origin and fixed advertised port.** The new origin validator rejects input that differs from the parsed canonical origin and rejects explicit/nondefault ports. The new Tor generator rejects a non-80 virtual port when an origin is configured. These changes prevent the documented origin and the generated service port from disagreeing and remove normalization ambiguity at the direct API boundary. The review found no new issue introduced by this diff. [Latest `kit/config/host-config.mjs:109-120`; `kit/adapters/tor.mjs:509-513`.]

These corrections are present at the pinned Tor-completion commit; latest main retains the baseline versions. No assertion is made that Tor completion was merged or deployed.
