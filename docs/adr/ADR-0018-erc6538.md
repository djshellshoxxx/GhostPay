# ADR-0018: ERC-6538 registry publish and lookup

Status: Proposed (proof of concept). Date: 2026-10-21. Gap: G-07 (docs/audits/01-completeness-audit.md). Code: `packages/chain-adapters/src/registry.ts`, `apps/web/src/features/registry/`.

**Not audited.**

## 1. Context

ERC-6538 defines a singleton registry mapping an address to its ERC-5564 stealth meta-address. Payers can look a payee up by wallet address instead of receiving the meta-address out of band. Publishing is a privacy trade-off: it permanently and publicly links the wallet address that sends the transaction to the meta-address.

## 2. Decision

- **Address.** One constant, `0x6538E6bf4B0eBd30A8Ea093027Ac2422ce5d6538`, copied from the Deployment section of EIP-6538 (CREATE2 through the deterministic deployer `0x4e59b44847b379578588920ca78fbf26c0b4956c`, salt `0x7cac4e512b1768c627c9e711c7a013f1ad0766ef5125c59fb7161dade58da078`). The EIP lists no chains; presence on any chain is **not assumed**.
- **Fail closed.** Every publish review, publish send and lookup first runs `eth_getCode` on the user's own RPC and refuses when the result is `0x` or malformed. The code hash is not pinned because no independently verified hash is available. Residual risk: an address with unexpected code. Mitigations: the address is shown to the user, the transaction is verified on the RPC after sending, and lookups strictly validate the returned bytes.
- **ABI.** Only `registerKeys(uint256,bytes)`, `stealthMetaAddressOf(address,uint256)` and `StealthMetaAddressSet` are included, with signatures copied from the reference `IERC6538Registry`. `registerKeysOnBehalf` is deliberately unsupported (no third-party or relayed registration).
- **Encoding.** Scheme id 1. The stored bytes are the 66-byte `spendPub33 || viewPub33` (the meta-address without `st:eth:0x`). Both directions run `decodeMetaAddress`, so off-curve or identical keys are rejected, and a stored value of any other length throws instead of being displayed.
- **Consent.** The UI shows the public-association warning, requires an unticked-by-default checkbox, a connected wallet, then a transaction review (network, contract, function, meta-address, calldata, value 0) before the send button exists. Changing network, consent or keys discards the review and the wallet connection. An RPC endpoint is required; there is no unverified path.
- **Lookup.** By wallet address. ENS is not implemented (it would add a trusted resolver and a second RPC surface); it stays a follow-up. The read-only call is previewed. The UI tells the payer to confirm the address with the payee out of band.
- **Mainnets.** The page lists only chains enabled in the chain config, so it follows the existing mainnet gating.

## 3. Testing

- `registry.test.ts`: encoding round trips, selector, validation, fail-closed paths.
- `RegistryView.test.tsx`: consent gating, review before send, post-send RPC verification, no-code refusal, missing RPC, lookup.
- `registry.anvil.test.ts`: the CC0 reference `ERC6538Registry.sol` (unmodified copy in `apps/web/src/features/registry/ref/`, SPDX CC0-1.0, from the ethereum/ERCs repository) is compiled with the local solc (pragma relaxed in a temp copy only) and placed at the canonical address with `anvil_setCode`. Our calldata is sent, the event is checked and our lookup decodes the result; a malformed stored value is rejected. Skips without anvil/solc unless `REQUIRE_ANVIL=1`. `setCode` means the reference's constructor immutables (domain separator) are not those of a real CREATE2 deployment; they are irrelevant to `registerKeys` and `stealthMetaAddressOf`.

## 4. Open items

Pin the runtime code hash per chain once verified from an official deployment; ENS lookup; a forge test using the reference (needs the file under `packages/contracts/test/`, coordinator decision, CC0 permits it); confirm registry presence per testnet by an on-chain check by a human.
