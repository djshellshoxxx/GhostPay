# Artifact metadata (for mirrors, verifiers and a future Replikrazy adapter)

The kit produces three versioned JSON documents. Each carries `schema` and `schemaVersion`; consumers must
refuse unknown schemas or higher versions rather than guess. No document contains wall-clock time, host secrets
or user data.

| Document | Where | Schema id | Version |
|---|---|---|---|
| Hosting manifest | `<topDir>/HOSTING-MANIFEST.json` inside the archive | `ghostpay.hosting-kit.manifest` | 1 |
| External references | `<topDir>/EXTERNAL-REFERENCES.json` inside the archive | `ghostpay.hosting-kit.external-references` | 1 |
| Mirror overlay | served at `<basePath>_mirror/mirror.json` by each mirror (generated by `profile`) | `ghostpay.hosting-kit.mirror` | 1 |

Plus two plain-text checksum files: `<topDir>/SHA256SUMS` (inside, `sha256sum -c` format, excludes itself) and
`<archive>.sha256` (next to the archive, never inside it).

## Hosting manifest v1 (normative fields)

```
schema            "ghostpay.hosting-kit.manifest"
schemaVersion     1
appId             [a-z0-9][a-z0-9._-]{0,79}
kit               { name, version }                    toolkit that wrote it
policy            { id, version, limits, allowSourceMaps }   inclusion policy that was enforced
content.root      "site/"
content.entrypoint  relative HTML path, e.g. "index.html"
content.files     [{ path, size, sha256 }] sorted by UTF-8 byte order of path
content.fileCount, content.totalBytes
content.digest    "sha256:" + hex(sha256(RFC 8785 canonical JSON of { entrypoint, files }))
provenance        { label, sourceDateEpoch|null, source: {kind:"git",commit,dirty}|{kind:"directory"}, notes[] }
trustSensitive    paths that look like app trust configuration (informational; bytes never changed)
metadataFiles     sorted top-level files other than site/** and SHA256SUMS
```

`content.digest` identifies the unpacked site independent of the archive container, compression, entry order and
timestamps. It is the value to publish and compare across mirrors. It covers **site bytes and paths only**: the
manifest's provenance, `trustSensitive`, OPERATOR.md and other metadata are not part of it, so a matching content
digest authenticates what is served, not who built it or how. The archive SHA-256 covers one exact archive file,
metadata included; publish both when provenance matters.

## Mapping to Replikrazy's draft ArtifactManifest

Replikrazy (`djshellshoxxx/replikrazy`) has an unmerged draft `ArtifactManifest` (`schemaVersion "1.0"`, `appId`,
`files: [{path,size,sha256}]` sorted by UTF-8 bytes, `entrypoint`) on branch `claude/trusting-goodall-9jdwxu`.
The kit does not depend on it and copies no code from it (that repository grants no licence). The field shapes were
chosen so that an adapter can build one without re-hashing:

```js
const draft = { schemaVersion: '1.0', appId: m.appId, files: m.content.files, entrypoint: m.content.entrypoint };
```

Its `artifactId` (a hash of its own canonical JSON including `appId` and `schemaVersion`) is a different value from
`content.digest`. An adapter must compute it with Replikrazy's own rules once those are final, and should check the
draft's stricter path rules itself (for example its 240-byte path limit matches the kit default; its rules are not
guaranteed to stay identical).

## Mirror overlay v1

`{ schema, schemaVersion, appId, releaseLabel, contentDigest, entrypoint, fileCount, archiveSha256|null,
mirror: { label, transport, publicOrigin|null, basePath }, notes[] }`.

It is served by the mirror itself, so it cannot prove authenticity. Its purpose is comparison: fetch it from
several mirrors over different networks and check that `contentDigest` agrees with a value from an independent
channel. Overlays live under the reserved `_mirror/` path and are never written into the archive's `site/`.
