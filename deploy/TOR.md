# Tor: what the onion service covers, and the real setup

> **Status: UNTESTED.** Nothing on this page has been run against a real Tor network: not the image build, not
> bootstrap, not reachability, not Tor Browser against the app. Treat it as a recipe until the smoke test below has
> been run and recorded here. The Tor, I2P, Nym and OHTTP profiles in `packages/net-transport` are marked
> `unverified` in code (`PROFILE_VERIFICATION`) for the same reason.

## What the onion service covers: the app files only

`docker compose --profile onion up -d` (or `selfhost.sh --onion`) builds `deploy/tor/Dockerfile` (Debian `tor`
package) and runs it with `deploy/tor/torrc`: v3 onion service, port 80 forwarded to `web:8080`, `SocksPort 0`,
`ControlPort 0`, logs to stderr, single-hop (non-anonymous) mode not enabled.

It serves the **web bundle** (HTML, JS, CSS) and, through nginx, the relayer under `/api/`. It does **not** carry:

- your **RPC traffic**: the browser talks to the RPC URL you configured, from the browser;
- your **wallet extension traffic**: the wallet uses its own RPC;
- anything on-chain: payer, amount, token, timing, announcement and sweep stay public.

## The real setup for a user who wants to hide their IP address

1. **Open the app in Tor Browser.** A web page cannot force a browser onto Tor or check that it runs in Tor Browser
   (`TOR_BROWSER_NOTICE`). Only Tor Browser itself routes the page's requests over Tor.
2. **Choose the RPC deliberately**, because the RPC provider still sees which addresses and block ranges you ask about:
   - **your own node**: behind TLS on loopback, or as its own onion service with an `https://` URL (the app's CSP
     `connect-src 'self' https: wss:` blocks plain `http://` RPC URLs, including `http://….onion`); or
   - an **`https://` RPC you trust**. Through Tor Browser it sees a Tor exit instead of your IP address, but it still
     sees every query.
3. Optionally load the app from the onion address, so the website host does not see your IP address either. This does
   not replace step 1 or 2.

Per-purpose selection (TM14): `packages/net-transport/src/selection.ts` and `apps/web/src/lib/defaultServices.ts` read
an optional `ghostpay.networkProfiles.v1` selection (`rpcProfile` and `relayerProfile`: `direct` or `tor-browser`;
`rpcMode`: `single` or `own-node`). It applies only after the first-use notices were acknowledged; otherwise the
default (direct, single RPC) applies. `tor-browser` is ambient: requests use the same `fetch`, and nothing is
verified. Settings exposes these per-purpose profiles and the own-node mode, with a first-use acknowledgment
before a non-default selection applies. Tor Browser and own-node status remain **unverified**; a profile label
is not proof of routing or endpoint ownership. `own-node` refuses an RPC URL that is not loopback or a v3 onion
URL, without contacting it, and rechecks the selection before each dispatch from a cached client.

The scan endpoint validator separately accepts plain HTTP loopback URLs for `local-proxy`, but the shipped CSP
allows only `'self' https: wss:` and `GHOSTPAY_CONNECT_ORIGINS` accepts only HTTPS/WSS origins. A cross-origin
plain-HTTP loopback proxy is therefore blocked by that policy. URL validation does not establish browser
reachability, and this document does not instruct the app to bypass the policy or fall back to another provider.
See the [source-pinned TM ledger](../docs/threat-model/TM_IMPLEMENTATION_20261118.md) and
[current completion report](../docs/handoffs/pages-completion-20261118/COMPLETION_REPORT.md) for qualification.

## Relayer behind Tor

- **Compose recipe** (onion -> nginx -> relayer): keep the relayer's `trusted-proxy` ingress. Every onion client then
  arrives from the Tor container, so they all share one rate-limit bucket.
- **Dedicated onion for the relayer** (Tor forwards straight to a loopback listener): set
  `"privacy": { "ingress": "onion" }` and `listen.host` to `127.0.0.1` or `::1`. The relayer then refuses any
  `trustedProxies` entry (a Tor client controls every header it sends), and the per-IP limits act as one shared onion
  budget. See `apps/relayer/PRIVACY.md`. Not tested with a real Tor.
- Add the `http://<addr>.onion` origin to the relayer `allowedOrigins` only if the SPA served from that onion should
  call it.

## Keys and address

- **Keys**: generated by Tor on first start inside the `tor-data` named volume. Nothing is in the repo (`.gitignore`
  also blocks `tor-data/` and `*.key`). Back up the volume if you need a stable address; anyone with it can impersonate
  your onion.
- **Address**: `docker compose exec tor cat /var/lib/tor/ghostpay/hostname`. An onion checksum catches typos; it does
  not prove the service is the one you intended. No mirror is described as verified.
- The server host and its operator remain a trust point. See `docs/remote/onion-i2p-research.md`.
