Start here (plain language)

GhostPay lets someone ask to be paid in a crypto asset without publishing their main wallet address for each sale. The seller makes a signed invoice. The buyer pays it from their own wallet. The payment goes to a fresh address made for that one payment. The seller later finds it with a private viewing key that stays in the seller's browser.

Two things are always true. First, the blockchain is public: anyone can see that a payment happened, roughly how much, and when. Second, GhostPay does not verify who the seller is. Check the people and records you rely on through channels you trust.

1. How a payment works

The diagram below shows the normal order of steps. It is also written as lists, so a screen reader or a text-only view gets the same information.

Seller

  1. Set up keys once. Create a key set and download an encrypted keystore. See section 2.
  2. Create an invoice. Choose the network, asset, exact amount, line items, expiry and fee policy. The invoice is signed with the invoice-signing key.
  3. Share the original file or link. Use any channel you trust. Anyone holding a bearer link can read it.
  4. Find the payment. Use Scan and receive with your viewing key. Scanning sends queries to the RPC provider you chose.
  5. Review and keep records. Optionally match the payment to the invoice, keep the receipt, and export backups.

Buyer

  1. Open the invoice. Paste or open the original link or file. GhostPay checks its format, signature and expiry.
  2. Check the deployment. Payment needs a verified deployment for that network. If none is present, the app blocks the payment.
  3. Connect a wallet. Choose the account and let the wallet switch to the invoice's network. See section 3.
  4. Approve in the wallet. Read each wallet prompt. Approve only the action shown. A token payment may first need an approval or a signed permit.
  5. Keep the reference. Save the transaction reference and the local record. Check the state shown before deciding anything else.

Hand-off: the seller sends the invoice to the buyer. The buyer returns the transaction reference or a receipt. Neither side should treat a message as proof of settlement without the checks in section 6.

In more detail

An invoice asks for a payment. It does not prove one happened. The payment goes to a one-time stealth address derived for that payment. The seller's viewing key lets the seller's browser recognise payments made to such addresses. The seller then reconciles what was found with the invoice. Reconciliation is a local suggestion until the seller confirms it.

Technical details: stealth addresses and announcements

The seller publishes a meta-address (a pair of public keys). A payer derives a one-time address from it and sends funds there. An announcement records enough data for the viewing key holder to detect the payment. This follows the ERC-5564 stealth address pattern, and the public registry follows ERC-6538. The contracts also route payments through GhostPay's router, which takes a 0.25% fee. Section 6 and the glossary explain what each state means.

2. Keys and backups

A key set has three keys. The spending key controls funds at the one-time addresses. The viewing key lets your browser find payments. The invoice-signing key signs invoices and receipts; it is optional for some flows. Anyone with the spending key can move funds at its one-time addresses, and losing it can lose them. Anyone with the viewing key can see your incoming payments, but cannot spend them.

A new key set exists only in the current tab until you export it or save an encrypted copy in this browser. Reloading or closing the tab without a backup loses it. Download the keystore before you depend on the keys, and confirm that it imports in another browser profile.

  1. Choose a passphrase of at least 14 characters. GhostPay also estimates strength and can refuse weak passphrases; it offers a generated suggestion.
  2. Store the keystore file and its passphrase in separate protected places.
  3. Optionally save the encrypted browser vault. It is a convenience copy in this browser, not a backup: clearing site data removes it.
  4. Keep other backups separate. Tag archives, reconciliation history and public configuration do not replace the keystore.

Technical details: key protection

Keystores use scrypt (N = 2^17) to derive a key from the passphrase, after NFKC normalisation, and AES-256-GCM for authenticated encryption. Idle lock is 15 minutes by default (range 1 to 240) and clears keys from memory; it does not erase stored records. Saved records live in this browser's IndexedDB, localStorage or sessionStorage as described in privacy and local data.

3. Connect a wallet

A wallet holds the account that pays. GhostPay does not hold it, and typing an address does not connect a wallet.

  1. Open the Pay view. GhostPay lists browser wallets that announce themselves. It uses the default browser provider only if no wallet announces.
  2. Choose the account. GhostPay asks the wallet to switch to the invoice's network. It asks once per connection and does not add networks to the wallet.
  3. Read each wallet prompt. A token payment may require an approval (exact to the invoice amount) or a signed permit before the payment itself. A permit is signed data, not a transaction.
  4. Disconnecting stops new requests from GhostPay. It does not cancel a request that the wallet has already received.

Wallet support is listed in the table in section 10. WalletConnect is Planned and not wired into the app. Hardware-wallet behaviour depends on the wallet you use and is not verified by this project.

Technical details: how requests are sent

Discovery uses EIP-6963 announcements, with the injected window.ethereum object only as a fallback. Chain switching uses wallet_switchEthereumChain once for the invoice's chain. Token approvals are exact to the invoice amount, and revocation sets the allowance to zero. Permits use eth_signTypedData_v4 when the token supports them.

4. Create an invoice

Use Create invoice to set the network, the asset, the exact amount, the line items, the expiry and the fee policy. A fixed token amount must be greater than zero. Each invoice needs at least one line item with a description, a quantity and a unit price. Memo text is limited to 500 characters. Expiry defaults to 24 hours and can be set from 1 to 2160 hours.

The fee policy decides who bears GhostPay's 0.25% router fee. Seller pays is the default: the payer sends the invoice amount and the seller receives the net amount. Payer pays adds the fee to the amount the payer sends, so the seller may receive up to one base unit more than the net figure.

A passphrase protects the invoice contents. It does not change whether the invoice can be paid. The browser sends the part after # only to your own page, not to a server, and GhostPay clears it from the address bar after loading by default. The link can still exist in chat history, screenshots, clipboard contents or a browser history entry.

Gas buffer (full build, token invoices only). A seller may accept an optional extra native-coin amount that the payer sends in the same transaction, so the one-time address can be swept without a linked wallet. The buffer is never refunded. It publicly links the payment, the one-time address and the payer, and its amount is an estimate, not a guarantee. Lean builds do not accept invoices with a buffer policy.

Matching is off by default. If you register an invoice for local matching, GhostPay can later suggest that a scanned payment corresponds to it. You confirm each suggestion. Registration never marks an invoice as paid.

Experimental Fiat-quoted invoices need a price feed and are available only in the full build on testnet feeds. Do not use them for real pricing.

Technical details: envelope and fragments

An encrypted invoice is an envelope with a version prefix (gpi=v1.) placed after #. Passphrase protection uses scrypt (N = 2^17) with AES-256-GCM. The envelope header is not authenticated until decryption succeeds, so do not rely on its visible fields alone. Plain envelopes carry no key at all.

5. Pay an invoice

  1. Open or paste the original invoice in Pay. Confirm the seller's signing key, network, asset, exact amounts and expiry against a source you trust. A valid signature shows that the invoice fields were signed by that key. It does not show who controls the key.
  2. Connect the wallet on the invoice's network (section 3). If the invoice has expired, GhostPay blocks the payment.
  3. Approve only the wallet prompts you understand. A rejected prompt (user refusal) is a clean stop.
  4. After the transaction is sent, GhostPay shows its state. Save the transaction reference and the local record before you close the tab.

An unknown outcome may already be on-chain. After a transaction is sent, any failure other than a user rejection is recorded as unknown. A timeout, disconnected provider or closed prompt does not prove nothing was sent. Check the wallet and the transaction reference before you start another payment. Clearing a local record only removes it from this browser. It cannot cancel a transaction.

Technical details: states GhostPay records

The app tracks a transaction through prepared, awaiting authorization, signed, broadcast attempted, broadcast unknown, pending confirmation, confirmed, failed, replaced, reorganised, unsupported and verification incomplete. A post-broadcast check reports whether the node already sees the transaction. A node that does not see it yet is shown as "not visible yet", not as a failure.

6. What counts as evidence

These checks answer different questions. None of them alone shows that the seller is who they claim to be.

Evidence states and what each one means
StateWhat it meansWhat it does not mean
Valid invoiceIts format and signature checks pass for the key shownSettlement. It is a request for payment
Valid seller receipt signatureThe signing key signed those receipt fieldsIndependent payment verification or the seller's identity
Observed or claimed paymentFound by scanning or recorded from a wallet or provider. The app shows it as claimed until it is finalVerified settlement
Pending (received, not final)The payment is seen, but has not reached the finality the app requiresFinal. A reorganisation can still remove it
VerifiedThe app checked the chain, transaction, recipient, asset and amount, and the transaction is finalProtection from future reorganisations beyond the stated finality, or from your provider being wrong
Imported historyA record restored from a backupAnything. It is untrusted until rescanned

Reconciliation statuses you may see include: an exact local match proposed (awaiting your confirmation), an ambiguous match that is not confirmed, no registered invoice matching the payment, a payment linked to a verified observation, an imported historical record that needs rescanning, and an observation invalidated after a reorganisation. Do not rely on an observation that the app marks invalidated.

A block explorer is a useful external view. Its operator receives your lookup, its indexing may lag, and providers can disagree. It is not a substitute for the app's checks.

7. Receipts and QR codes

A seller receipt is a signed, canonical JSON record of payment fields. Binding a receipt to an invoice means loading the original signed invoice, checking the matching fields, and giving consent. A bound receipt is stronger evidence of consistency than a loose one, but it still does not prove settlement by itself.

In the full build, a manually typed digest can be signed into a receipt. The app labels it seller-supplied, not matched. Treat it as a note, not as proof that the invoice was checked. The lean build refuses signing a receipt that is not bound to an invoice.

To check a receipt later, reimport the original receipt JSON in the Pay view. This requires a prepared payment and your consent. The verification checks the signature and the expected invoice fields. A receipt does not decrypt or restore keys.

Keep the original file. A QR code is a representation of the data, and a photo or screenshot of it may be incomplete or separated from its context. The original receipt file is the record to keep.

9. Share public configuration and settings

Public seller configuration can be exported as QR, text or a file. It contains public keys, the supported networks and a check value. Compare the public keys on both devices before you rely on the preview. The check value detects accidental changes. It does not authenticate the sender or prove the data is recent.

Settings exchange carries preferences by default: the delay range, idle-lock timeout, theme and address-bar clearing. Primary and second-provider RPC URLs, the relayer URL and pinned signer keys are optional sections. They are not ticked by default, so review each one before you export. Anything you tick leaves the device in the export file or QR code.

Camera use starts only when you request it. If the camera is unavailable or permission is refused, use the file import instead.

10. RPC and network configuration

An RPC URL is the address of a node provider. Your browser asks it for chain data such as balances, transactions and logs. GhostPay ships no hard-coded EVM RPC endpoints. You enter a primary URL and may add a second one for comparison.

  • Use an https:// address. The Settings check does not accept plain http, including localhost, on this path.
  • Test sends one chain-identity request (eth_chainId) to the address in the field, when you click it. It can test a value you have not saved. It sends no credentials and does not follow redirects.
  • A second provider is optional. When set, the reads that verify a deployment are compared with the primary. If the two disagree, the check fails and payments stay blocked until a later check agrees. Scanning withholds the checkpoint for any page where the providers disagree and scans that page again. The app does not retry a disagreement. Scanning also asks the second provider for block heights and blocks, to cap each page and corroborate anchors. Outside the deployment check and scanning, other calls, including transaction sends, use the primary only. A second provider also sends these queries to a second operator.
  • What a provider learns: your IP address, the addresses and transaction data your requests name, and when you ask. A provider can log this. Choose an operator you trust, or run your own node if you can.
  • Do not put secrets in a URL you save. Saved settings are stored in this browser without encryption, and a key in a path or query string is visible there.

Technical details: endpoint validation and fail-closed behaviour

Endpoint validation accepts https (and wss, which the browser transport refuses). Requests omit credentials and refuse redirects. The optional second provider is used for verification only when it is set. The app's verification check compares each covered read and does not retry, so a mismatch is not hidden. The library also contains a reconciled client that retries once after a short pause for tip races; the app does not use it. On a mismatch the deployment becomes unverified, so payments stop.

11. Privacy in brief

Stealth addresses reduce address reuse for the seller. They do not hide the public transaction graph. Moving funds from a one-time address to a wallet you already use can link the payment to that wallet. The privacy page has a feature-by-feature matrix showing what each action reveals, where data is stored, and what is not yet protected.

The app has no analytics, telemetry, third-party scripts or remote fonts. Outbound requests go to the page's own host and to endpoints you enter or choose in the app, such as RPC, scan, relayer, wallet and chain-node addresses, plus a merchant profile URL when you press Load. These statements describe the app code. They do not describe your hosting provider, network, browser or extensions.

12. Merchant guidance

A merchant workflow today is: set up keys and back them up; create one invoice per sale; share it; scan for payments; review matches yourself; keep receipts and exported backups. Keep aggregate bookkeeping outside the app. GhostPay's beta and v1.0 focus on private payments and recovery; excluded products have no scheduled restart.

13. Contextual help in the app

Some controls in the app have a small ? button. Its explanation is also available to screen readers.

  • Keyboard: press Tab to reach the button. Press Enter or Space to keep the explanation open, and press again to close it.
  • Mouse and touch: hover, or tap the button. Tapping elsewhere closes an explanation you opened.
  • Escape closes an open explanation without changing the control it describes.
  • Explanations never cover a control. They take space in the page flow and wrap on narrow screens.

On this page, sections marked Technical details are disclosures. Open them with the keyboard or mouse. They work without JavaScript.

14. Technical glossary

Terms are listed in the order a reader is likely to need them. The app's own wording may differ slightly.

Announcement
An on-chain record that helps a viewing-key holder notice a stealth payment. It is public.
Bearer link
An invoice link that contains its own decryption key. Whoever holds the complete link can read it.
EIP-1193 provider
The standard interface a browser wallet exposes so that apps can request accounts, chains and signatures.
EIP-6963
A standard that lets several installed wallets announce themselves to a page, so the app can list them.
Permit (EIP-2612)
A signed message that authorises a token allowance without a separate approval transaction. Signing it does not move funds by itself.
Finality
The point after which a transaction is treated as settled, according to the rules the app applies. Before that point a reorganisation can remove it.
Fragment
The part of a URL after #. Browsers do not send it to the server in the request.
Idle lock
Clears keys from memory after a period without input. Default 15 minutes. Stored records are not erased.
Invoice signature
A signature by the seller's invoice-signing key over the invoice fields. It proves the key signed them, not who holds the key.
Keystore
The encrypted file that holds a key set, protected by a passphrase.
Deployment manifest
The verified description of a payment deployment on one network. Without one, the app blocks payments on that network.
Meta-address
The public keys a seller publishes. Payers derive one-time addresses from it.
Observation
A record that a payment-like event was seen. An observation is not settlement until it is verified.
One-time (stealth) address
An address derived for a single payment. Funds sent to it can be found with the viewing key.
RPC endpoint
The address of a node provider that answers chain queries. It sees the queries you send.
Reorganisation (reorg)
A change to the chain's recent history that can remove or replace transactions.
Receipt binding
Checking that a receipt's fields match a specific signed invoice.
Relayer
A service that submits a transaction for you in exchange for a fee. A relayer sees what it submits.
scrypt
A password-based key derivation function. The app uses N = 2^17 for passphrase-protected data, which makes guessing expensive.
AES-256-GCM
An authenticated encryption scheme. Tampered ciphertext fails to decrypt.
NFKC
Unicode normalisation applied to passphrases, so visually identical text gives the same key.
Spending key
The private key that controls funds at one-time addresses. Keep it secret and backed up.
Viewing key
The private key that lets your browser find payments. Anyone with it can see your incoming payments, but not spend them.
Invoice-signing key
The key that signs invoices and receipts.
Sweep
Moving funds from a one-time address to a destination you choose. The destination can link the payment to that address.
Testnet
A test network with worthless funds. All payment paths in this build are testnet only.
Unknown outcome
A state for a sent transaction whose result the app cannot confirm. Check the wallet and chain before acting again.

15. Accessibility and layout

  • Every page works with a keyboard. Focus is always visible, and the Skip to help link is the first stop.
  • Diagrams are written as ordered lists, so no information depends on colour or position alone. Status labels always include text.
  • Tables scroll horizontally inside their own box at narrow widths. The page itself does not scroll sideways at 320 CSS pixels or at 200 percent browser zoom.
  • Motion is removed when your system asks for reduced motion. The app uses system fonts only, so no font file is downloaded.
  • This page loads its own stylesheet, favicon and no script. Printing hides navigation and shows the disclosures.
